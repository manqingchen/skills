# contract-align：后端文档 × OpenAPI 契约的字段对齐

在 prd-to-flow 拆解完成、后端技术文档到位之后，把「前端要什么」钉死到「后端真给什么」上。

## 铁律：未确认必问清，不清晰必问到清晰

**本条最高优先级，覆盖全文一切相反的省事做法。** 违反任何一条即流程失败；「有推荐就不问」「替后端猜答案」「含糊答复当确认」一律禁止：

1. **未确认的问题必须问到确认结果**：把问题真正问出去（自包含：上下文、候选、推荐），并**拿到明确的确认结果**才能给对应字段下结论。确认结果从哪来不用管——用户直接回答、用户去问相关方、实测接口、参照实现均可——唯一硬要求是：没拿到确认结果，就不能下结论。推荐方案不是跳过提问的理由。
2. **不清晰的必须问到清晰**：含糊的答复（「应该是吧」「先这样」）必须追问一次；文档与契约的歧义（一词多义、两可、状态机不明）必须问到一个不含糊的答案。追问后仍不清晰的，该条目标「待确认」，禁止当作已确认使用，禁止静默采用推荐值或自行推导值。
3. **问了没等到回答**：显式列出待确认清单继续等；可并行处理其他接口，但相关条目在 03 中必须保持「待确认」状态且在交付说明里可见，后续轮次继续追问直到有答案。
4. **用户关掉提问框 ≠ 默许**：改为文字列出问题等回复。
5. 唯一豁免：用户明确说「先不用处理/别问了」——照做，但该条目在 03 待确认清单里注明「用户拍板挂起」及日期，不消失。

**核心原则：OpenAPI 契约是唯一事实源，后端文档只是意图声明，前端技术方案只是需求清单。三者对不上、或有多种对法的地方，一律问用户拿到确认结果，禁止自行拍板。**后端文档里会有无用字段、过期字段、同名异义字段——这个流程的目的就是把它们筛出来、把每个字段的判定依据留档。条件允许时（见 0.5/5.4），同需求的已写实现是第四个信息源：它既能在开工前免费回答许多待确认项，也能在收尾时当产物的 oracle——但它只提供证据，不构成仲裁，与用户拍板冲突时列冲突待用户定。

**只做契约对齐。** 不重新拆解、不改 PRD 口径、不生成业务代码——那是 prd-to-flow 和执行阶段的事。

## 流程总览

```
0.   定位输入           → prd-to-flow 产出目录 + 后端技术文档，缺哪个补哪个
0.5  基线重申（必做）    → 继承的约束逐条判断本阶段是否仍适用（尤其实现分支可否参照）
1.   提取前端字段需求    → 接口清单 + 每个接口的消费字段与用途（来自技术方案与任务卡）
1.5  数据流载体盘点（必做）→ 每个数据需求枚举到达载体（新接口/页面主接口/既有接口），补齐文档没列的改动面
2.   拉取真实契约        → 逐接口调 gz-global-api 脚本，拿到测试环境实际 schema（含载体盘点出的主接口）
3.   三源比对与判定      → 接口级 + 字段级，逐条判成 ✅确认 / ⚠️需提问 / ❌需提问
3.5  决策项建模（提问前必做）→ 归并决策项 × 全部影响面；同一决策项的所有表现面一次问全
4.   即时提问           → 分批问用户（问题自包含），确认结果落决策记录
                          ↳ 每条答复入库前与既有决策做一致性回溯，冲突必须回写
5.   增量产出           → 新建 03-contract-align.md + 原地更新 02-tech-design.md 与受影响任务卡
                          ↳ 任务卡回写按「结论→影响面」推导（判定逻辑/验收标准/场景表/mock 口径）
5.4  实现对照终检（条件允许时强烈推荐）→ 抽查实现分支 diff 作第四源，纠偏产物
6.   自检               → 逐条对照检查清单
```

第 4 步的每一个问题都必须真的问出去、**拿到确认结果**才能给对应字段下结论——带推荐方案也不例外。确认结果未必立刻到手，**未确认的条目标「待确认」并继续处理其他接口，不要干等，更不要替任何人猜答案**。

## 0. 定位输入

需要两样东西，先确认都在：

1. **prd-to-flow 产出目录**：`~/.claude/prd-flow/workspace/<JIRA号>/`（至少含 `02-tech-design.md`）。用户没给 Jira 号时，读 `~/.claude/prd-flow/README.md` 索引，列出候选让用户选；目录不存在时本流程不启动，提示用户先跑 prd-to-flow。
2. **后端技术文档**，接受三种形态：
   - 文件路径（`.md` / `.docx` / `.pdf` / `.txt`），用 Read 读
   - 网页链接（飞书/语雀/Confluence/wiki），用 WebFetch 读；无法访问时明确告知，请用户粘贴内容
   - 用户直接粘贴的文本

读到后端文档后先做**接口级清点**：文档里涉及哪些 `/os/...` 接口，与 `02-tech-design.md` §4 的接口依赖清单对一遍。文档里多出来的接口（后端新增/本期范围外）和清单里文档没提的接口，都列入第 4 步提问。

### 0.5 基线重申（必做）

拆解阶段拍板的约束会跟着产出与上下文**静默流入本阶段**，但两个阶段的目标不同，约束未必仍适用。开工前把继承的前提逐条列出并判断，重点三类：

1. **实现参照类**（如「忽略某实现分支」「按从零视角拆解」）——这是拆解阶段为估工作量设的约束；对齐阶段的目标是「确认后端真实给什么」，同需求的已写代码是仅次于 OpenAPI 的事实源。**发现仓库里存在同需求实现分支时，必须问用户「对齐阶段是否可参照实现分支/已合入代码」**，不许沿用禁令。
2. **范围类**（只拆前端/某端不在范围）——通常仍适用，确认即可。
3. **拆解遗留的未决问题**——检查是否已被后端文档或 OpenAPI 天然回答，能自答的不要带进提问。

结论写入 03 头部备注（如「本阶段参照实现：无 / feat/xxx 分支」）。

## 1. 提取前端字段需求

从前端产物里把「要什么字段、做什么用」整理成清单，三个来源按序收集：

1. **`02-tech-design.md`**：§4 接口契约与后端依赖清单（接口 × 前端调用点 × 就绪状态）、§4.2 消费字段表、§4.3 待确认依赖项（D 项）。这是主来源。
2. **任务卡** `tasks/T0xx-*.md`：其中引用接口字段做判定/渲染/埋点参数的条目（如「`qualification !== 3` 时展示按钮」「埋点属性 `deposit_eligible` 取自 xxx」）。埋点参数若依赖接口字段或枚举映射，一并纳入。
3. **（可选，cwd 是业务仓库时）前端实际消费点**：grep 技术方案里列出的 service / types 文件，把每个字段的消费位置落到 `file:line`。有代码证据的条目在映射表里标出处。

产出一张**字段需求表**（本步中间结果，在回复里简短呈现）：接口 × 前端用途 × 期望字段 × 证据位置。没有期望字段名的用途（如「保证金是否充足的标记」）也要列出——这正是后面最需要和后端对齐的条目。

### 1.5 数据流载体盘点（必做）

接口清单不能只取「后端文档 ∪ 前端期望」的并集——**两边都没提的改动面会整体漏掉**。最典型的形态：后端把新字段内聚塞进页面/列表的**既有主数据接口**下发，而不在文档接口表里列（收藏/详情/购物车这类聚合接口尤其常见）。前端期望清单里通常也看不到它，因为拆解时假设数据走新接口——那是一个**未被验证的载体假设**。

做法：对字段需求表里每个**数据需求**，枚举它可能的到达载体：

| 载体形态 | 判别方法 | 核实动作 |
|---|---|---|
| 新增专用接口 | 前端期望契约里的新路径 | 按清单拉 OpenAPI（第 2 步主体） |
| 所在页面/列表的主数据接口 | grep 该页面实际调用的 service URI | **也拉一次 OpenAPI**，核对新字段是否已内聚下发 |
| 其他既有接口（设置/摘要/计数类） | 按用途推 | 同上，仅在用途沾边时核 |

主接口核出新字段而文档没列的：补进对齐范围，标注「文档未列，OpenAPI 证实」，并在第 4 步问用户「以哪个载体为准」（前端期望的新接口 vs 主接口直出，影响请求数与刷新方式）。

## 2. 拉取真实契约

对接口清单里的每个 `/os/...` URI 运行 gz-global-api 的提取脚本：

```bash
python3 "<本skill目录>/../gz-global-api/scripts/extract_openapi.py" "/os/user/personal/getUserAttr" --method GET
```

- 路径解析：优先取本 skill 同级的 `../gz-global-api/scripts/extract_openapi.py`；不存在则依次尝试 `~/.zcode/skills/gz-global-api/scripts/`、`~/.claude/skills/gz-global-api/scripts/`。
- `--method` 已知时必传（技术方案 §4.1 的表格、前端 service 调用里都有）；省略时脚本会返回该 path 全部方法，多方法且不确定用哪个的列入提问。
- stdout 是裁剪后的标准 OpenAPI JSON（目标 operation + 传递依赖），stderr 有映射与 `Source file`。
- **遵守 gz-global-api 的领域规则**：路径映射 `/os/{service}/...`、`product` 服务的例外（Swagger 端点无 `/os/product` 前缀且 paths 已含全路径）、Swagger 404 即判「不符合约定」，禁止换域名换服务重试、禁止猜其他端点。
- 脚本失败（网络不通 / 404 / 非 JSON）时：如实告知用户该接口未能取到契约，该接口整体标「❌ 契约不可得」，**不允许退化为「只按后端文档对齐」**——文档不是事实源。

## 3. 三源比对与字段判定

对每个接口，把三方信息摊开比对：**前端需求（第 1 步）× 后端文档（第 0 步）× OpenAPI 实际 schema（第 2 步）**。逐字段判成四类：

| 判定 | 条件 | 动作 |
|---|---|---|
| ✅ 确认 | 文档与 OpenAPI 均有该字段，类型/枚举/语义一致，且与前端用途明显对应 | 直接写入映射表，依据写「文档+OpenAPI 一致」 |
| ✅ 以 OpenAPI 为准 | OpenAPI 有、文档未提及，且字段名与前端用途**明显对应**（如 `xxxEnough` / `xxxStatus` / `isXxx`，无需解释即可理解） | 写入映射表，标注「文档未提及，以 OpenAPI 为准」 |
| ⚠️ 多候选/冲突 | 文档中有 ≥2 个字段都能满足前端用途；或文档与 OpenAPI 的类型、枚举值、含义对不上；或 OpenAPI 有、文档未提但对应关系**靠猜** | 列入第 4 步提问，附候选与推荐 |
| ❌ 缺失/疑似无用 | 前端要的字段两边都没有；或文档里的字段 OpenAPI 里不存在（无用/已下线）；或字段存在但取值逻辑说不清（如「资格判定按哪个字段、状态机怎么走」） | 列入第 4 步提问 |

判定纪律：

- **「明显对应」拿不准就升级提问**。判断标准是：不看任何背景解释，一个字段名能否唯一对上一个前端用途。能才叫明显。
- 枚举值逐个核（文档说 5 个值、OpenAPI 只有 4 个，就是 ⚠️，典型如 `qualification` 四态 vs PRD 五态带 `unknown`——后者其实是前端兜底口径，这类「谁的职责」也要问清）。
- 文档里 OpenAPI 不存在的字段，一律进第 5 步的「无用/未接入字段」清单，不要因为「文档写了」就采信。
- 判定结果先在回复里汇总呈现（多少 ✅、多少 ⚠️/❌），再进入提问。

### 3.5 决策项建模（提问前必做）

把所有 ⚠️/❌ 与口径分歧先**归并成决策项**：一个决策项 = 一个不可再分的产品口径（例：「某个枚举多了后端态、少了产品态时，每个多余态怎么处置」是一个决策项，不是两个）。每个决策项列出它的**全部表现面**——从字段需求表和任务卡里找：标签展示、筛选参数值、入口/按钮判定、二次确认条件、埋点 status 口径、mock 造数……一条不能漏。

规则：

- **一个决策项的所有表现面必须在同一次提问里问全**。把同一决策项的表现面拆到不同批次，等于给「前后两次答复自相矛盾」留门——用户在两批问题里对同一口径给出不同答案，是实际发生过的高频事故。
- 决策项之间有依赖的（如筛选值依赖展示映射），排同一批或显式注明先后。
- 分批排序仍是「先结构后口径」，但**批的切分单位是决策项**，不是把问题凑够 4 条。

## 4. 即时提问协议

这是本流程的核心交互。**问题必须自包含——脱离本轮对话上下文也能看懂**，每条含：

```markdown
**Q1. `/os/user/personal/getUserAttr` 的「保证金是否充足」用哪个字段？**
- 前端用途：引导模块的保证金标签（Eligible / Insufficient Balance），前端不比对金额
- 候选：
  - `bargainRequiredBalanceEnough`（boolean，OpenAPI 存在，文档 §2 提及）
  - `bargainWhitelist`（boolean，OpenAPI 存在，但语境更像「白名单免保证金」）
- 推荐：`bargainRequiredBalanceEnough`
→ 用哪个？若是白名单逻辑，两个字段的判定关系是什么？
```

规则：

- **分批问，每批 ≤4 条**。先问会改变前端判定逻辑/接口级范围的，再问枚举口径、命名确认类的。
- 每条必含：接口 URI、候选字段（含类型与在哪一方出现过）、前端用途、推荐。**问逻辑的条目要问到「怎么判断」**（如：状态怎么流转、什么条件返回什么值），不只问字段名。
- 用户给出的确认结果**逐条记入决策记录，注明日期**，按结论更新判定。确认结果本身含糊（「应该是 A 吧」）时追问一次，仍含糊就标「待确认」。
- **答复一致性回溯（每条答复入库前必做）**：新答复与既有决策逐条比对。发现同一口径两说时，**禁止只把新答复挂进待确认**——必须回到旧决策修正（标注「修正 + 日期 + 依据」）并同步所有引用它的任务卡与技术方案指针；修不动（需后端仲裁）就把两条都标「冲突待仲裁」并在 03 显著位置警示。跨批次的答复之间是冲突高发区，别只盯着本轮问题。
- 未确认/未问完的条目标「待确认（等确认结果）」，不阻塞其他接口的对齐与产出。
- 禁止行为：替后端选字段、把 ⚠️ 悄悄降级成 ✅、因为「有推荐」就不问、一次抛 20 条、新答复与旧决策矛盾却两边都保留。

用户中途带着确认结果回来继续时（新一轮对话也常见）：直接从第 3 步的判定表恢复，只消化新结论，不重拉已确认接口（除非用户点名重查）——但**一致性回溯照做**。

### 5.4 实现对照终检（条件允许时强烈推荐）

两个前置判断：0.5 基线重申中用户开放了实现参照；或对齐中发现同需求实现已存在于某分支/主干（`git log --grep <JIRA号>` 一查便知）。**产物是「文档 → 文档」，没有外部事实检验就没有验证回路**——实现 diff 是现成的 oracle，抽样比对就能抓住文档视角的系统性盲区。

做法（抽样即可，不必全量）：

1. **service 层 types**：实现的字段名/类型/枚举 vs 03 映射表——抓「OpenAPI 有但实现不消费」「实现消费但两边都没有」。
2. **判定工具/常量文件**（枚举映射、有效状态集合、分流函数）vs 决策记录——抓口径分歧与等价简化（如决策用三字段组合分流、实现只用其中两个）。
3. **筛选/入参映射** vs 03 的参数决策。
4. **页面主数据接口的类型扩展** vs 数据流盘点结论——抓文档没列的内聚下发面。

## 常见坑

- **把后端文档当事实源**：文档会滞后、含无用字段、同名异义。只有 OpenAPI 反映代码现状；文档与 OpenAPI 冲突时不是「二选一」，是提问。
- **拆解约束静默继承**：为估工作量而「忽略实现分支」的拍板，到对齐阶段反而屏蔽了最权威的信息源之一，待确认项被无谓挂起、文档没列的改动面被漏掉。每个阶段开工先重申基线。
- **按文档清单圈对齐范围**：后端把新字段塞进页面主接口的「内聚下发」不会出现在文档接口表里；不做数据流载体盘点，整个改动面 invisible。
- **OpenAPI 有就悄悄采用**：字段名与用途「明显对应」才能自动确认且必须标注；对应关系需要解释的，都是提问项。
- **同一决策项拆批问**：分批提问里同一口径前后两说是高频事故；只挂起新答复不回写旧决策 = 带着内部矛盾交付。
- **只回写字段引用**：验收标准和场景表也吃契约结论；不修剪的话，下游会对着不可能达标的验收干活。
- **问题写得依赖本轮对话上下文**：缺 URI、缺候选、缺用途的问题，离开对话就看不懂，确认方来回澄清全浪费在补上下文上。
- **只问字段名不问逻辑**：「用哪个字段」答了，「什么条件返回什么值、状态怎么流转」没问，前端判定逻辑还是写不出来。逻辑类条目必须问到判断规则。
- **一次抛出全部问题**：用户会草率回答。分批 ≤4，先结构后口径。
- **干等确认结果**：一个接口的待确认项挂住全部产出。未确认的标状态、继续处理其他接口。
- **重跑全量重来**：重复拉契约、重复问已答过的问题，用户会烦。03 文档就是为增量续跑设计的。
- **拿实现压用户拍板**：实现对照发现与用户决策冲突时，实现只是证据不是仲裁者——列冲突待用户定，不擅自改决策。
- **越界改动**：顺手重写 02 的设计、重新拆任务卡、直接开写业务代码——都超出本流程，收住。
