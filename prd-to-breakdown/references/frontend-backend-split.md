# 前端 / 后端职责切分规则

拆解需求时用它回答一个具体问题：**这条需求里的每一段逻辑，到底该谁做？**

---

## 一、判断准则

只有一条准则，其余都是它的推论：

> **这段逻辑放在前端，会不会导致「换个客户端就能绕过它」，或者「必须在 Web / iOS / Android / 小程序 各实现一遍」？**
> **会 —— 就是后端的。**

推论出三条硬规则：

1. **凡是涉及安全、权限、数据的，一律后端**——前端代码运行在用户设备上，用户能改、能跳过、能直接调接口。前端的任何校验都只是"礼貌"，不是"保证"。
2. **凡是多个客户端都要用的业务规则，一律后端**——否则同一条规则要在 N 个端重复实现 N 次，改一次漏一处就是线上事故。
3. **凡是"判断"和"呈现"能分开的，判断归后端、呈现归前端**——后端返回 `canCancel: true/false`，前端负责把它渲染成可用/禁用按钮。这是切分得最干净的模式，优先采用。

---

## 二、四层归属

| 层 | 归属 | 判断依据 |
|---|---|---|
| 展示与交互 | 前端 | 只影响这台设备上看到什么，不影响任何数据的正确性 |
| 业务逻辑 | 后端 | 影响数据的写入结果或多端一致性 |
| 校验 | **两端都做，职责不同** | 前端为体验（即时反馈），后端为安全（强制执行） |
| 契约与枚举 | 后端定，前端消费 | 前端一旦硬编码业务含义，后端改枚举就会静默出错 |

---

## 三、不该交给前端的逻辑（逐条说明）

### 1. 权限与角色判断

- ❌ 前端判断"这个用户是管理员，所以显示删除按钮"→ 前端只要 `if (role === 'admin')`，但接口没校验，任何人用 curl 就能删
- ✅ 后端在接口层强制校验；前端根据权限**渲染**按钮显隐
- 常见变体：数据权限（只看自己部门的）、字段级权限（手机号脱敏）

### 2. 业务规则与状态机

- ❌ 前端判断"订单已发货就不能取消"
- ✅ 后端裁决并返回可操作标记：

```
{ "status": 3, "canCancel": false, "cancelDisabledReason": "订单已发货" }
```

- 这样前端连规则文案都不用自己编，规则变更时后端改一处即可

### 3. 金额 / 库存 / 价格 / 优惠 / 积分计算

- ❌ 前端 `total = price * count * discount`——浮点误差、优惠叠加规则、四舍五入方式都可能和后端不一致，用户看到的金额和实际扣款对不上
- ✅ 后端计算并返回最终金额；前端只做展示（金额格式化规则也由后端或统一工具函数提供）
- 库存同理：前端判断"还有货"再让下单，并发下必然超卖

### 4. 数据过滤与范围

- ❌ 前端拿到全量列表再 `filter` 出"我自己的"
- ✅ 后端在查询层加条件
- **特别注意：搜索和排序**——如果列表是分页的，前端筛选/排序只作用于**当前页**，用户会看到"搜不到明明存在的数据"。这个 bug 极其常见，判断方式是问一句：「数据是分页加载的吗？」是——就必须后端做。

### 5. 幂等与去重

- ❌ 前端提交后禁用按钮防重复提交
- ✅ 禁用按钮只是体验优化（网络重试、用户刷新页面都能绕开）；后端必须用幂等键 / 唯一约束 / 分布式锁兜底

### 6. 枚举含义、错误码、字典映射

- ❌ 前端维护 `const STATUS_MAP = { 1: '待支付', 2: '已支付' }`
- ✅ 后端返回含义，或由后端提供字典接口；前端不硬编码业务含义
- **但展示层的纯样式映射可以留前端**（如 `status === 1 ? 'blue' : 'gray'` 的颜色选择），前提是它不影响业务判断

### 7. 跨端共用逻辑

- 只要有两个以上客户端，"这段逻辑在哪儿实现"的答案默认就是后端
- 典型：表单校验规则、排序规则、分页规则、活动资格判定

### 8. 串联操作与事务

- ❌ 前端依次调「创建订单」「扣库存」「发消息」三个接口
- ✅ 后端一个接口内事务完成；前端只调一次，失败时整体回滚
- 前端串联的后果：中间某步失败，数据处于不一致状态且没有回滚手段

## 四、不该交给后端的逻辑

反向也要判断，否则会把不该往返服务端的东西做成接口，白白增加延迟和后端负担：

| 逻辑 | 归属 | 说明 |
|---|---|---|
| 纯 UI 状态（展开/收起、当前 tab、hover） | 前端 | 不需要持久化就不要往返服务端 |
| 展示格式化中的本地部分（宽度自适应、本地化排布） | 前端 | 只与设备/语言有关的部分 |
| 输入框即时格式提示（必填标记、手机号位数） | 前端 | 但后端仍要独立校验一次，不能因此省掉 |
| 图片裁剪、压缩、缩略图 | 前端 | 上传前处理；后端仍要校验文件类型、大小、真实内容（只信 magic number，不信扩展名） |

## 五、灰色地带：怎么判

这些不能靠套规则，要看具体情况：

| 场景 | 判断方式 |
|---|---|
| 搜索过滤 | 数据一次性全量加载 → 前端可做<br>分页加载 → **必须后端**（否则只搜当前页） |
| 排序 | 同上。另外看排序字段是否包含后端才知道的信息（如热度、权重）——包含则必须后端 |
| 路由守卫 / 页面拦截 | 前端路由守卫是体验（防止误入空页面），**不能替代后端鉴权**；后端必须对每个接口独立校验 |
| 表单校验 | 前端做即时反馈（失焦提示），后端做强制校验；**规则要单一来源**——理想是后端返回校验规则/枚举供前端消费，至少保证两端规则一致并有测试覆盖 |
| 字段脱敏 | 后端做（前端脱敏等于把明文发给了客户端，抓包即得） |
| 状态管理 / 缓存 | 前端管本地 UI 状态；业务数据的权威副本在后端。前端缓存失败会导致"用户看到的是过期状态" |
| 第三方 SDK 对接 | 看密钥：密钥不能进客户端 → 后端代理；纯展示型 SDK（如地图渲染）→ 前端 |
| 埋点上报 | 前端采集、后端落库与聚合 |
| 文件上传 | 前端选择与预校验，后端校验与存储；**大文件直传对象存储时，签名由后端下发**，客户端绝不持有长期密钥 |

## 六、职责切分表（产出格式）

对每条需求填一行，**不允许留空**：

| 需求 | 前端职责 | 后端职责 | 前端不处理（明确排除） | 归属结论 |
|---|---|---|---|---|
| R1 订单取消 | 取消按钮 + 二次确认弹窗 + 结果 toast + 列表状态刷新 | 状态机校验、权限校验、库存回补、操作日志 | 不判断"能否取消"，只消费 `canCancel` | 后端主导 |
| R2 状态时间线 | 时间线组件、空态展示 | 历史数据接口、排序、老数据兼容 | 不前端拼接时间文案与顺序 | 后端供数，前端展示 |
| R3 列表页样式调整 | 全部 | 无（不涉及接口变更） | — | 纯前端 |

**「前端不处理」这一列是这张表的核心价值。** 它显式声明了排除项，防止开发者出于"顺手"把业务判断写进组件——那正是后续多端不一致、以及"改了一处忘了一处"的源头。

---

## 七、落到任务卡上

判定完归属，必须继续做两件事，否则这张表只是纸面结论：

1. **拆成对应的任务卡**：一个需求同时涉及两端时，拆成前端卡 + 后端卡，不要合成一张（合成后无法分配给两个人并行）
2. **接口契约单独成卡并前置**：契约卡（定字段、定枚举、定错误码）排在前端卡和后端卡之前。这样契约一定，前后端就能真正并行开发，而不是前端干等后端写完

任务卡的「类型」字段填 `前端` / `后端` / `联调`，让任务总览表能按端筛选出各自的工作量。

## 八、自查

拆完后逐条问：

- [ ] 有没有哪条任务卡里，前端在判断业务规则而不是消费后端标记？
- [ ] 有没有校验规则前后端各写一套、且没有单一来源？
- [ ] 分页列表的搜索/排序是不是后端做的？
- [ ] 每个涉及数据的接口是否都独立校验了权限（而不是依赖前端不显示入口）？
- [ ] 涉及金额/库存/积分的地方，计算是否都在后端？
- [ ] 同时涉及两端的需求，是否拆成了两张卡而不是一张？
- [ ] 接口契约是否只有一份定义、且排在前端卡之前？
- [ ] 职责切分表里每条需求的「前端不处理」列是否都有内容？
