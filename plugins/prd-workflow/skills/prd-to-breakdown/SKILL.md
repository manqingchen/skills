# PRD → Flow：需求拆解为可执行任务流

把一份 PRD 变成「每个任务都能被一个人、独立、在一天内做完并验证」的任务流。

**核心原则：拆解的质量取决于对现有代码的理解，而不是对 PRD 的复述。** PRD 只告诉你「要什么」，代码库才告诉你「从哪儿改、改多少、会和谁冲突」。所以本流程的第二步（反向调研）通常比第一步更花时间，不要跳过。

## 铁律：未确认必问清，不清晰必问到清晰

**本条最高优先级，覆盖全文一切相反的省事做法。** 违反任何一条即流程失败；「先做后问」「有推荐就不问」「自行脑补补齐」一律禁止：

1. **未确认的问题必须真的问出去**：用提问框（分批 ≤4 题、自包含）或文字列出，等到用户的明确回答才能给对应条目下结论。「有推荐方案」不是跳过提问的理由——推荐只是让用户确认/纠正只需一句话。
2. **不清晰的必须问到清晰**：含糊的答复（「应该是吧」「差不多」「先这样」）必须追问一次；PRD、文档、答复中的歧义（一词多义、两可、范围不明）必须问到一个不含糊的答案。追问后仍不清晰的，该条目标「待确认」，禁止当作已确认使用，禁止静默采用推荐值或自行推导值。
3. **问了没等到回答**：显式列出待确认清单继续等；可以并行处理其他条目，但相关条目在产出中必须保持「待确认」状态且在交付说明里可见，下一轮继续追问直到有答案。
4. **用户关掉提问框 ≠ 默许**：改为文字列出问题等回复。
5. 唯一豁免：用户明确说「别问了，按推荐/直接拆」——照做，但被跳过的问题全部写进产出的「待确认」表，注明「按推荐执行，未经确认」。

## 流程总览

```
0. 读取 PRD          → 拿到原始需求，确认范围边界
0.5 确认拆解范围      → 问清这次拆「前端 / 后端 / 前后端」，之后所有步骤按此聚焦
1. 反向调研当前项目   → 摸清技术栈 / 模块结构 / 既有约定 / 可复用实现
2. 差异与缺口检查     → PRD × 现状 对不上或说不清的地方，列出来问用户
3. 职责归属切分       → 逐条需求判定：前端做 / 后端做 / 前后端都做（各做什么）
4. 需求拆分          → Epic → Feature → 任务卡（颗粒度：可独立开发+可验证）
5. 技术落点          → Epic 级「结构设计」+ 每条任务写清文件、改法、接口/数据结构变化
6. 依赖与排期        → 依赖图、可并行分组、里程碑切分
7. 写入状态库        → 需求 / 任务 / 验收 / 契约 / 决策 / 埋点
8. 自检             → 逐条对照检查清单
```

各步骤之间**不要跳步**。第 2 步的每一个待拍板问题、第 0.5 步的范围确认，都按顶部**铁律**执行：必须真的问出去、等到明确回答；含糊答复追问到清晰；用户拒绝回答时用文字列出等回复，回复前对应条目不得当作已确认。问题多时分批问（每次不超过 4 题），但必须批完所有问题，不允许「问几条、其余写进文档」。

## 0. 读取 PRD

从以下来源之一拿到需求：

- 用户消息里直接粘贴的需求文本
- 用户给出的文件路径（`.md` / `.docx` / `.pdf` / `.txt`），用 Read 读取
- 项目里的 PRD 目录（常见位置：`docs/`、`doc/`、`prd/`、`需求/`、`requirements/`、`*.prd.md`）
- **Confluence / wiki 链接（`cwiki.guazi.com`）——不要请用户粘贴，直接下载**，见下方「0.1 Demand collection」
- **设计稿 / 原型**（自包含单文件 HTML、Figma / 蓝湖链接、设计稿截图）——PRD 里常以附件或链接形式出现，不要只读正文

### 0.1 Demand collection：需求原文统一入库

用户给出 wiki 地址时，**主动调用 cwiki-download 技能下载**，存进 `~/.prd-to-breakdown/demands/`，不再让用户手工下载或粘贴。

**重拉已入库的 wiki 时，先对版本元数据再对内容**：优先比对文档里的「当前版本 / 更新时间」（或页面 `page-version`、`last-modified`），一致就直接答复「未变更」；只有元数据变了才做内容 diff。不要一上来就 diff 正文——版本没变时 diff 只会浪费一轮，还容易把格式抖动当成变更。

```bash
# 1) 确定存放目录：已知 Jira 用 demands/<JIRA>，未知用 demands/_inbox
DEMAND_DIR="$HOME/.prd-to-breakdown/demands/${JIRA:-_inbox}"
mkdir -p "$DEMAND_DIR"

# 2) 调 cwiki-download（SKILL_ROOT = 该技能目录；run.sh 会自行处理软链与登录态）
CWIKI_SKILL_ROOT="$(dirname "<cwiki-download/SKILL.md 的绝对路径>")"
bash "$CWIKI_SKILL_ROOT/run.sh" "<wiki URL 或 pageId>" --output-dir "$DEMAND_DIR"

# 3) 登记到状态库（路径以实际下载结果为准）
python3 "$PTB" demand add --url "<wiki URL>" --page-id "<pageId>" --title "<页面标题>" \
  --path "$DEMAND_DIR/<标题>-<pageId>.md" \
  --llm-path "$DEMAND_DIR/<标题>-<pageId>.llm.md" ${JIRA:+--jira "$JIRA"}
```

规则：

- **优先读 `.llm.md`（模型阅读版）**：复杂表格已被转成结构化文本，比人读版更适合拆解；
- **技术方案 / 接口文档类 wiki 同样入库**：后端技术方案、接口契约说明等 wiki 链接也用 cwiki-download 下进 `demands/<JIRA>/` 并 `demand add` 登记——它们是 contract-align 与联调阶段的输入，与 PRD 同目录管理，不要散落在业务仓库 `docs/` 里；
- 下载失败（`E_NO_COOKIE` / `E_MISSING_CREDENTIALS`）→ 按 cwiki-download 的提示让用户初始化 `guazi-sso-login`，**不要在本流程里收集账号密码**；此时可请用户先粘贴正文，并把「需求原文未入库」写进 `risk`；
- 文件落盘后**只读本地文件**，不再回头请求网页；`demands.path` 是后续拆解的唯一输入；
- 先不知道 Jira 号时归入 `_inbox`，确定后 `python3 "$PTB" demand attach --id <D号> --jira <JIRA>`（路径不移动，以库记录为准）；
- 重复下载同一 URL 会按 URL 覆盖登记，不产生重复记录。

### 设计稿登记（UI 需求必做）

**拆解阶段不执行 UI 还原，但必须登记设计稿：** 只记录路径与「哪份稿覆盖哪些任务」，像素值、色值、断点一律留给 ui-restore 提取。

- 需求含 UI 改动（新增/调整页面、组件视觉）时，先确认设计稿位置，**用 `ptb design add` 登记（路径 + 覆盖的任务）**，并在任务的 `design_ref` 里标注对应区块。
- **没有设计稿**：按顶部铁律提问索取。用户明确说「没有设计稿」后才可继续，此时用 `decision add` 记「无设计稿，视觉以项目现有组件为准」，而不是留空。
- **一份设计稿可能覆盖多张任务卡**：登记时写清覆盖关系（例如「列表页设计稿 → T001/T003/T004/T005」），执行阶段按「一份稿一轮」组织还原，而不是每张卡各跑一遍。
- **登记时判断设计稿是否为「缩放舞台」**：自包含 HTML 里若有固定宽度画布（如 `2048px` 的 `.stage`）+ JS `transform:scale()`，它的一切绝对像素都是舞台坐标，不能直接落地。把舞台宽与渲染比例写进 `design add` 的 note，并在 `jiras.baseline` 提示「落地尺寸需按参照物比值换算」。这一条是给执行侧（ui-restore）的输入，拆解阶段不换算、只传递。

拿到后先做三件事，都要在回复里简短说明：

1. **需求清单化**：把 PRD 里所有「要做什么」编号列出（R1、R2……）。这一步是为了后面能逐条对齐，避免拆着拆着漏了。
2. **范围边界**：明确写出**不做什么**（PRD 里说"暂不支持/后续迭代"的，以及明显属于其他需求的）。边界不清的需求是范围蔓延的源头。
3. **识别缺失的验收标准**：PRD 常常只写功能不写验收。哪条需求你无法判断「做完没有」，记下来，进入第 2 步提问。

> 如果输入根本不是需求文档（例如是一份 bug 列表、一份代码 review 意见），先跟用户确认这是不是要拆的对象，不要硬套本流程。

## 0.5 确认拆解范围（前端 / 后端）

**读完 PRD、动任何调研之前，先问这一句。** 范围决定后面所有步骤的聚焦面：反向调研扫哪些目录、职责切分表填几列、任务卡产出哪一端、排期按哪一端的工时算。

### 引导提示（照这个问）

读完 PRD 后，先给出一句话的需求概括，再问：

> **这次要拆的是哪一端？**
> - **A. 只拆前端**——我按前端视角拆，后端只作为依赖列出（需要哪些接口、要什么字段）
> - **B. 只拆后端**——我按后端视角拆，前端不展开，但要给出接口契约供前端对接
> - **C. 前后端都拆**（默认）——完整职责切分 + 两端任务卡，并标出哪些能并行

如果 PRD 里已经明确限定（例如通篇只讲页面改版、或明确是接口/数据层需求），不要机械发问——直接说出你的判断和依据，让用户确认或反驳：

> 「这份 PRD 通篇是页面交互和样式调整，没有接口和数据变更，我按**只拆前端**来做。如果后端也有改动，告诉我一声。」

### 三种范围下的产出差异

| 范围 | 反向调研 | 职责切分表 | 任务卡 | 技术方案 |
|---|---|---|---|---|
| **A 只前端** | 只扫前端目录、组件库、请求封装、状态管理 | 仍要填全，重点在「前端不处理」列——明确列出哪些逻辑**等着后端给** | 只出前端卡 | 前端改动细节 + **接口依赖清单**（要调什么、要什么字段、谁提供、是否已存在） |
| **B 只后端** | 只扫服务端目录、数据层、路由与中间件 | 仍要填全，重点在后端职责 | 只出后端卡 | 数据模型 + **接口契约**（前端拿这份就能开发）+ 迁移与回滚 |
| **C 都拆** | 两端都扫 | 完整 | 两端卡分列 | 完整 |

### 关键：只拆一端 ≠ 另一端可以不知道

即使只拆一端，也要产出「另一端依赖清单」，否则接不上：

- **只拆前端时**，必须列出：需要调哪些接口、每个接口要什么字段、接口是否已存在（存在则写路径，不存在则标「待后端提供」并写出期望契约）。这些是前端能不能开工的前提，缺了这份清单，前端任务卡里就会出现「等后端」的阻塞项而没人知道卡在哪里。
- **只拆后端时**，必须给出接口契约的完整定义（字段、枚举、错误码、分页），这是交给前端的交付物。没有它前端无法并行开工。

> **范围只影响「展开到多细」，不影响「另一端完全消失」。** 另一端永远以「依赖 / 契约」的形式在文档里出现。

### 记录范围

确认后，把结论写进 `jiras.scope`，并在后续对话中始终按此范围产出。用户中途改范围（例如「后端也一起拆了吧」）时，回到第 3 步重做职责切分表，再补出另一端的任务卡——不要只在原文档上追加，那会导致两端口径不一致。

## 1. 反向调研当前项目

**按第 0.5 步确认的范围聚焦调研面**：只拆前端就只扫前端目录，不必花时间读服务端代码；只拆后端同理。唯一例外是查明「另一端是否已有可复用的实现」——这仍然值得扫一眼，能避免把已有的接口又拆一遍。

**目的：让每条任务卡里写的是真实的文件名和真实的函数名，而不是「在相关模块中添加逻辑」。**

### 调研方式

先判断项目规模：

- **小项目（< 约 50 个源文件）**：直接自己用 Glob / Grep / Read 扫。
- **中大型项目**：用 Agent 工具并行派发（各 agent 一个主题，互不重叠），典型分工——A 整体架构（技术栈/目录/构建/依赖）、B 相关业务模块（同类功能与代码位置）、C 数据层（模型/表/迁移/ORM）、D 接口层（路由/鉴权/请求响应约定/错误码）。派发时要求 **只回结论 + 路径 + 关键代码位置**，不要回大段原文。

### 必须搞清楚的七件事

| # | 要搞清的问题 | 为什么重要 |
|---|---|---|
| 1 | 技术栈与版本、构建与启动命令、测试命令 | 任务卡里的验收步骤要能真跑起来 |
| 2 | 模块划分与目录约定 | 决定新代码该放哪儿 |
| 3 | 数据模型与持久化方式（表、迁移、ORM） | 需求改动常从数据开始 |
| 4 | 接口/组件约定（路由、鉴权、错误处理、状态管理、样式方案） | 新代码必须和既有写法一致 |
| 5 | **是否已有相似实现可复用或需改造** | 这是拆解时最大的信息量来源 |
| 6 | 约束与坑（遗留代码、正在进行的重构、已知技术债、必须兼容的旧版本） | 决定哪些任务风险高、要单独拆 |
| 7 | **同类能力的既有实现**（状态共享 / 定时刷新 / 提醒·角标类） | 决定新代码「怎么组织」而不只是「放哪儿」：本项目同类功能用 Provider / hook / service 怎么分层。至少列 1 个同类实现，写明复用或不复用的理由 |

### 探测：双引擎项目索引（codegraph + ast-grep）

两个引擎分工不同，缺一不可：**codegraph 回答「谁依赖谁、改动波及谁」，ast-grep 回答「这个模块内部长什么样」。** 仓库根有 `.codegraph/` 时先建索引（不属于某个需求，落在 `~/.prd-to-breakdown/index/<repo>/`，不进业务仓库）：

```bash
python3 "$PTB" index ensure --root <项目根>         # 开工先保鲜：没建过就全量 init，建过就增量 sync
python3 "$PTB" index show  --root <项目根>          # 看模块地图与规则命中
python3 "$PTB" index show  --root <项目根> --module components/layout   # 单模块
```

`index ensure` 的判定：`.codegraph` 缺失或 codegraph 版本变了 → 优先从同仓其它 worktree 的索引**播种**（相对路径可复用，实测 56s → 26s），播种失败才全量 `init`（旧库自动备份为 `.codegraph.bak-<时间>`）；否则 `sync` 增量对账；ast-grep 无索引可同步，只在仓库 HEAD 变化或工作区有未提交改动时重扫。**每轮拆解开头跑一次即可，不要手动 `init`**（全量 34~56s，增量 2s）。需要强制重建时用 `index build`。

**git worktree 场景**：每个 worktree 是独立目录、索引不共享。建完 worktree 可先预热——`python3 "$PTB" index ensure --root <新 worktree> --background` 立即返回，日志在 `~/.prd-to-breakdown/index/<slug>/ensure.log`。**不要用软链共享 `.codegraph`**：codegraph 是单写者模型，两个 worktree 并行会把符号刷成对方分支的内容。

- **codegraph 三问**：`query <英文标识符>` 盘点同类实现 → `callers` / `callees <符号>` 看依赖方向与消费方 → `impact <符号>` 看改动波及面；
- **ast-grep 七类约定**：`provider-definition`（状态放在哪些 Provider）、`hook-export`（有哪些可复用 hook）、`http-request`（请求是否收口在 service）、`storage-access`、`i18n-usage`、`timer-schedule`（轮询/延时）、`event-bus`（静态图断链处，必须人工配对发布与订阅）。

四条硬约束：

- **先英文化再查**：两个引擎都做词法/结构匹配，不做中文语义匹配（中文查询实测返回 0 条）。把 PRD 概念翻成标识符（降价角标 → `priceDropBadge` / `collectReminder`）再查，用过的关键词记进 brief；
- **只信 `--json`**：codegraph 符号不存在、仓库未初始化都返回退出码 0，彩色文本判不出真假；
- **结论写成 `symbol@file#Lx-Ly` 或 `rule:<规则名>@file#Lx-Ly`**，这是 `validate` 唯一能核验的格式；
- **无索引就退化 grep**，并在 brief 对应行标 `[grep 退化]`——不允许静默降级。

### 模块级分析（只分析本需求涉及的模块）

1. PRD 概念 → 英文标识符，`codegraph query` / `explore` 找候选符号，按目录聚成 2~5 个候选模块；
2. 对候选模块跑 `index show --module <目录>` + `callees <符号>`，得到该模块的职责分布与跨模块依赖——一个 Provider 挂十几个 callees、横跨轮询/订阅/请求，就是「混职责」的可量化信号；
3. 对候选模块跑 `callees` / `callers` / `impact`，确认谁在消费它、改动会波及谁；
4. 据此写第 5 步的「结构设计」，依据优先用 `symbol@file#Lx-Ly` 与 `rule:<规则名>@file#Lx-Ly`。

### 输出：项目现状摘要（Project Brief）

在正式拆解前，用一段简短的话说明：

- 技术栈一句话（语言/框架/数据库/关键库）
- 与本需求相关的模块地图（3~7 个模块，各自职责 + 关键文件路径）
- 现有相似实现（如果有，指出路径，并判断「复用 / 改造 / 新写」）
- 约定清单（命名、目录、接口风格、测试方式）
- 风险与约束

这份摘要要放进最终文档，它是后面所有任务卡能落到具体文件的依据。

## 2. 差异与缺口检查

把 PRD 和项目现状放在一起对，找出需要用户拍板的问题。**分类找，别泛泛地问「还有补充吗」。**

### 四类缺口

1. **PRD 内部矛盾或遗漏**
   - 同一条需求前后描述不一致
   - 只写了正常流程，没写异常流程（失败、超时、空数据、越权、并发）
   - 只写了功能，没写边界（数量上限、字段长度、超大文件、重复提交）
   - 没有验收标准，无法判断做完没有

2. **PRD 与现状冲突**
   - PRD 描述的行为和现有代码逻辑不一致（要改旧行为？还是新增分支？）
   - 依赖的能力当前项目没有（需要引入新库/新服务/新权限）
   - 数据模型对不上（PRD 里要的字段现有表里没有，且涉及历史数据迁移）

3. **范围与优先级不明**
   - 多条需求里哪条是必须的、哪条可以延后
   - 是否需要数据埋点、灰度开关、兼容旧版本
   - 多端（Web / iOS / Android / 小程序 / 服务端）分别要做什么

4. **交付约束不明**
   - 截止时间、可投入人力、是否需要拆分给多人并行
   - 是否要求不破坏线上数据、是否需要回滚方案

### 提问格式

**先调研、带方案地提问**，不要空手问。对每个问题给出你基于代码调研得出的**推荐答案**，用户只需要确认或纠正——这比开放式提问快得多：

```markdown
### 待确认问题

**Q1. 旧数据的 `status` 字段如何迁移？**
- 现状：`orders` 表已有 `status`（0/1/2），本次 PRD 要求改为 5 个状态
- 推荐：新增 `status_v2` 字段 + 双写 + 后台任务回填，旧字段保留一个版本周期
- 备选：直接改枚举值并一次性刷数据（有回滚风险）
→ 需要你确认走哪种
```

**口头变更必须有固定入口**：用户口头口径与 PRD 冲突时（「产品刚说的」「这样改一下」），当场做三件事——`decision add` 记录变更内容与生效范围；`risk add` 按模板记「wiki 未同步，验收以本条 decision 为准」；追问一句「是否已让产品更新 wiki」。禁止只在对话里改了实现而不落记录：验收文本不可变，文档滞后时 decision 是唯一口径。

**问题多时分批问完，不许降级**：数量多不要一次全抛。先问会**改变拆解结构**的（范围、数据模型、是否改造旧逻辑），再问产品口径类的（字段命名、埋点口径、交互取舍、频控归属、异常处理策略），分批把**所有**问题问完。判断「要不要问」的标准是**这条是否需要人拍板**，而不是「是否改变拆解结构」——凡涉及用户可感知行为、数据口径、跨端职责的问题都必须问，即使你已有明确的推荐答案。唯一例外：用户明确说「别问了，按推荐直接拆」。

## 3. 职责归属切分（前端 / 后端）

**这一步必须在拆分之前做。** 归属没定清楚就拆任务，会出现三种典型事故：前后端各做一遍同一件事；都以为对方会做，最后线上没人做；把后端该管的业务判断塞给前端，导致多端（Web/iOS/Android/小程序）逻辑不一致且能被绕过。

**判断准则只有一条：这段逻辑放在前端，会不会导致「换个客户端就能绕过它」或「需要在多个端重复实现」？会——就是后端的。**

### 三层归属模型

| 层 | 归属 | 内容 |
|---|---|---|
| **展示与交互层** | 前端 | 渲染、样式、布局、动画、交互反馈、loading/空态/错误态、输入框即时校验与错误提示位置、表单收集 |
| **业务逻辑层** | **后端** | 业务规则、状态流转、金额与库存计算、发号、去重、幂等、权限判定、数据范围过滤（数据权限）、审批流 |
| **校验层** | **前后端各做一次，职责不同** | 前端：为了即时反馈、提升体验，不做安全保证<br>后端：**唯一的强制校验**，任何请求都当作不可信 |
| **契约与枚举层** | **后端维护，前端消费** | 状态枚举、错误码、字典表、展示格式化规则（金额精度、时间格式、脱敏规则）、分页结构 |

### 速查：这些逻辑不让前端处理

- 权限与角色判断——前端只控制"按钮显不显示"，后端必须独立校验；前端隐藏了按钮不等于接口安全
- 业务规则与状态机——"这个状态能不能取消""满足什么条件才能提交"由后端裁决，前端只按后端返回的可操作标记来渲染
- 金额、库存、价格、优惠、积分的计算——前端不做，浮点误差和并发超卖都会出事
- 数据过滤与范围——"只看自己部门的""只看自己创建的"由后端在查询层保证
- 幂等与去重——重复提交由后端用幂等键/唯一约束兜底，前端禁用按钮只是体验优化
- 枚举含义、错误码、字典映射——后端维护，前端不硬编码业务含义
- 跨端共用的业务逻辑——只要有两个以上客户端，逻辑就必须在后端
- 数据一致性相关的串联操作（下单扣库存、退款改状态）——后端事务

### 速查：这些不该让后端处理

- 展示格式化中纯本地的部分（如宽度自适应、本地化排布）
- 纯 UI 状态（展开/收起、当前 tab、hover）——不必往返服务端
- 输入框的即时格式提示（手机号规则、必填标记）——但后端仍要独立校验一次

### 输出：职责切分表

对**每一条需求**（R1、R2……）填一行，不允许留空：

| 需求 | 前端职责 | 后端职责 | 前端不处理（明确排除） | 归属结论 |
|---|---|---|---|---|
| R1 订单取消 | 取消按钮、二次确认弹窗、结果 toast、列表状态刷新 | 状态机校验、权限校验、库存回补、写操作日志 | 不做"能否取消"的判断，只消费接口返回的 `canCancel` | 后端主导 / 前端对接 |
| R2 状态时间线 | 时间线组件、空态展示 | 提供历史接口、排序、老数据兼容 | 不前端拼接时间文案，展示格式由后端给定 | 后端提供数据，前端纯展示 |

**「前端不处理」这一列是必须的**，它才是这一步真正的价值——明确排除项能防止开发者出于"顺手"把业务逻辑写进组件里，那正是后面多端不一致的源头。

### 特殊情况

- **纯前端需求**（样式调整、无接口改动）：后端职责写「无」，并注明"不涉及接口变更"
- **纯后端需求**（定时任务、数据修复）：前端写「无」，并注明"对前端不可见"
- **一个需求内混合**：切成两条任务卡（前端卡 + 后端卡），中间以接口契约连接，接口契约作为独立的先行任务
- **归属有争议时**：列入第 2 步的待确认问题，带推荐方案问用户——这属于会改变拆解结构的决策，值得问

详细判断规则与反模式见 `references/frontend-backend-split.md`，拆解前读一遍。

## 4. 需求拆分

### 层次结构

```
Epic（本次需求的几个大块，通常 2~5 个）
  └── Feature（用户可感知的功能单元，每个 Epic 下 2~6 个）
        └── Task（任务卡：可独立开发、可独立验证）
```

### 任务卡的颗粒度标准

一条任务卡**必须**同时满足：

- **一个人**能做（不需要多人同步协调）
- **一次会话 / 一天内**能做完（超过就继续拆）
- **有明确的完成信号**（能跑一个命令、点一个页面、过一条断言来验证）
- **不依赖未完成的其他任务**——或者依赖关系在卡里写明了

拆得不够：`「实现订单模块」`、`「优化性能」`、`「对接第三方」`
拆得合适：`「新增 GET /api/orders/{id}/timeline 接口，返回状态变更历史」`、`「订单列表页接入分页，默认每页 20 条」`

**如果一条任务卡里出现了"并且"、"同时"、多个动词——继续拆。**

### 拆分视角（按顺序都过一遍，避免漏任务）

1. **数据层**：表/字段/索引变更、数据迁移、数据回填脚本
2. **服务端**：接口、业务逻辑、校验、权限、定时任务、第三方对接
3. **前端/客户端**：页面、组件、状态管理、路由、请求封装、交互细节（loading / 空态 / 错误态）
4. **联调与配置**：接口联调、开关配置、环境变量、CI 变更
5. **测试**：单元测试、集成测试、手工验证用例
6. **交付配套**：埋点（按曝光/点击分型，见下）、监控告警、灰度、文档、回滚方案

> **不要漏掉"看不见的活"**：数据迁移、错误处理、权限校验、埋点、兼容旧数据、日志监控。这些往往占实际工作量的一半，漏掉它们会让排期失真。

> **埋点按类型拆、位置落到组件**：禁止写成笼统的「加埋点」。曝光（进入可视区域触发）用 `TrackBeseen`、点击用 `sendTrack`，各自挂哪个组件/元素、什么时机触发都要写进卡；点位不清或口径有歧义（埋在容器还是每个 item、点击还是确认后）时进第 2 步提问。

## 5. 技术落点

每条任务卡里写清楚「改哪儿、怎么改」，这样接手的开发者（或另一个 agent）不用重新调研。

对每条任务写明：

- **端归属**：前端 / 后端 / 联调。来自第 3 步的职责切分表，不要在这里临时改判
- **涉及文件/模块**：具体路径，能到文件级别就到文件级别（`src/api/order.ts`、`internal/handler/order.go`）
- **改动方式**：新增文件 / 修改现有函数 / 删除 / 重构。**「新增 vs 修改」必须以仓库现状为锚，不能凭 PRD 场景推导**——产出清单后逐个核对路径存在性：路径已存在的一律判「修改」，并把既有行为列入回归面（PRD 描述的结构性大改最容易把「改造存量组件」误判成「新写组件」，回归范围与工作量随之失真）。凭印象写「新增」而仓库里已有同名实现，同样是事故
- **接口契约**：新增或变更的 API——方法、路径、请求体、响应体、错误码
- **数据结构**：新增或变更的表字段、类型定义、状态枚举
- **复用点**：可以复用的现有函数、组件、工具类（写路径）
- **设计锚点（含 UI 改动的任务必填）**：设计稿路径 + 本卡对应的设计区块（区块名或选择器）+ 所属设计稿页面。
  **这里只登记映射与路径，不抄 px / 色值 / 断点**——像素值的提取与落地由 ui-restore 负责，两边都写必然对不上。
  「复用 X 组件」只是组件级判断，不等于「视觉上就该长成 X 的默认样子」：卡片上必须同时写明它对的是稿里哪个区块
- **埋点落点**：涉及埋点的任务必须写明埋点类型、挂在哪个组件/元素、什么时机触发，并按类型选对上报 API——**曝光埋点（进入可视区域触发）用 `TrackBeseen`，点击埋点（点击/交互触发）用 `sendTrack`，两类禁止混用**（混用会让曝光量/点击量口径直接作废）。埋点清单只在 `tracking_points` 里定义一次，任务只引用不复制
- **风险点**：兼容性、并发、性能、数据一致性上的注意项
- **文件行只登记在创建它的任务上**：同一文件被多张卡触碰时，只有首次创建（`add`）那张登记文件行；后续任务改同一文件，在 implementation 里写「扩展 T00X 创建的 <路径>」即可，**不要**再登记 `modify` 行——`validate` 的存在性检查只认当前仓库，文件未创建前登记 `modify` 必然报「文件不存在」，返工的是整副任务卡

### Epic 级「结构设计」（一页，不是每卡一份）

任务卡回答「改哪儿」，本节回答「怎么组织」。缺了这一层，执行方只能临场发挥——典型事故是一个 Provider 同时管刷新策略/节流/轮询/接口兜底/事件订阅，或一个组件塞进角标+hover+主动提醒+关闭计时。五个决策项逐项写，每项必须有依据：

| 决策项 | 要写清什么 | 典型反例 |
|---|---|---|
| 模块边界与依赖方向 | 谁调谁、禁止哪条反向依赖 | 组件直接请求，绕过 service |
| **状态归属** | 数据谁 own、谁只消费（Provider / hook / 组件） | 计数状态塞进渲染组件，多处各存一份 |
| 数据流向 | 写入点 → 存储 → 消费点的单向链路 | 多个组件各自 fetch 再合并 |
| 抽象判定 | 复用 / 改造 / 新建 + 理由 | 为一次性逻辑造通用抽象 |
| 分层约定核对 | 状态→Provider、请求→service、时间与纯逻辑→utils、单文件 ≤200 行 | 一个文件同时管状态与展示 |

**依据列只认五种值**：仓库路径（`components/layout/X/index.tsx`）、brief 小节（`## 模块地图`）、codegraph 查询结果（`symbol@file#Lx-Ly`）、ast-grep 规则命中（`rule:<规则名>@file#Lx-Ly`）、`缺口→已进第 2 步提问`。写「按项目惯例」「合理分层」这类纯文字不合格，`validate` 会报错。

落库：写进 brief 的 `## 结构设计` 小节（`jira set --brief-file`），相关任务的 `implementation` 引用对应决策。

锚点示例（OS-43617 复盘）：**计数状态归 `PriceDropBadgeProvider`，提醒规则（7 天阈值 / 数量变化判定）独立成 `usePriceDropReminder` hook，`CollectIcon` 只做渲染与挂载**——拆解时写上这条，事后「把提醒逻辑从巨型组件里抽出去」的返工就不会发生。

**接口契约是前后端任务的连接点，必须单独成卡或单独成节。** 前端任务卡只引用契约，不重新定义字段名；后端任务卡是实现契约的一方。契约先行，前后端才能并行开发——否则前端只能等后端写完。

**不要写实现代码**。技术方案止于「契约与落点」，写代码是执行阶段的事。
但**「不写实现代码」≠「不记录设计锚点」**：设计稿路径、区块映射必须写进任务卡；像素、色值、断点不在这一步落地，留给 ui-restore。

## 6. 依赖与排期

- **依赖图**：明确标出 A 必须先于 B（`T3 依赖 T1、T2`）。跨模块的接口契约类任务应当排在依赖它的开发任务之前——先定契约，再并行开发。
- **可并行分组**：把无依赖关系的任务分组，标注「可并行」和「建议并行开发人数」。
- **里程碑**：按"能跑通/能演示"的节点切分。例如 M1 数据层就绪、M2 后端接口可用、M3 前端联调完成、M4 测试与灰度。每个里程碑写清**可验证的产出**，而不是「大致完成」。
- **关键路径**：指出哪条链路决定整体工期，这是排期风险点。
- **工作量估计**：用 S（半天内）/ M（1~2 天）/ L（3~5 天）分级，并说明理由。不要给没有依据的精确小时数。

## 7. 产出：写入状态库

**唯一产物是 `~/.prd-to-breakdown/prd.db`（SQLite），不生成任何 md 文档，不写业务仓库。** 所有读写通过 CLI，禁止手写 SQL、禁止直接改库文件。

```bash
SKILL_DIR="$(cd "$(dirname "<本技能目录>/SKILL.md")" && pwd -P)"
PLUGIN_ROOT="$(cd "$SKILL_DIR/../.." && pwd -P)"
PTB="$PLUGIN_ROOT/scripts/ptb.py"
```

`<本技能目录>` = 本 SKILL.md 所在目录（若是指向插件源码的软链，`pwd -P` 会解析到真实路径）；`PLUGIN_ROOT` 即 `plugins/prd-workflow/`。长文本一律用 `--xxx-file /tmp/xxx.md` 传入——`/tmp` 只是传输载体，不是产物。

### 建需求与设计稿登记

```bash
python3 "$PTB" init
python3 "$PTB" jira add --jira OS-43558 --title "代理商 iframe 嵌入" --scope frontend \
  --brief-file /tmp/brief.md \
  --baseline "布局复用项目既有页面；断点以项目为准；设计稿只校对控件级样式" \
  --out-of-scope-file /tmp/scope.md
python3 "$PTB" design add --jira OS-43558 --path /tmp/proto.html --covers "T001,T003,T004,T005"
```

- `scope` 取 `frontend` / `backend` / `both`，与第 0.5 步的确认结果一致；
- `brief` 放第 1 步的项目现状摘要（技术栈、模块地图、复用判断、约定、风险）；
- `baseline` 放基线约束（如「复用现有布局优先于设计稿」「忽略某实现分支」），task-runner 开工前会逐条复核。

### 写需求条目

```bash
python3 "$PTB" req add --jira OS-43558 --id R1 --title "店铺车源列表页" --priority must \
  --description-file /tmp/r1.md --acceptance-file /tmp/r1-acc.md \
  --excluded-frontend-file /tmp/r1-excl.md
```

### 写任务、文件、验收、验证

```bash
python3 "$PTB" task add --jira OS-43558 --id T003 --title "列表页编排" --end frontend --estimate M \
```

- 不生成任何 md（任务卡、总览表、i18n、索引都没有）；需求列表用 `python3 "$PTB" jira list`，任务总览用 `python3 "$PTB" jira show --jira X --md`；

### 配套产物落位：验证脚本、草稿与文档不进业务仓库

拆解与执行过程会产生几类「配套产物」，统一落在 `~/.prd-to-breakdown/` 下，**不要散落在业务仓库根目录或业务仓库 `docs/` 里**：

| 产物 | 落位 | 说明 |
|---|---|---|
| 需求原文 / 后端技术方案 / 接口文档 | `demands/<JIRA>/` + `demand add` 登记 | 技术方案是 contract-align 与联调的输入；优先读 `.llm.md` |
| 任务本地配套产物（Playwright `.mjs` 验证脚本、i18n 文案草稿等**不被业务仓库构建引用**的文件） | `tests/<JIRA>/` | 验证脚本运行命令用 `verify add --cmd` 登记；已在库里登记过旧路径的，用 `task text --field notes` 补迁移说明 |

验证脚本移出仓库后的依赖解析：脚本开头用 `createRequire` 锚定业务仓库根——`PROJECT_ROOT` 环境变量可覆盖，默认值写创建时的仓库绝对路径——再 `require('playwright')` 等项目依赖，例如：

```js
import { createRequire } from 'node:module';
const PROJECT_ROOT = process.env.PROJECT_ROOT || '<业务仓库绝对路径>';
const require = createRequire(`${PROJECT_ROOT.replace(/\/+$/, '')}/`);
const { chromium } = require('playwright');
```

业务仓库内**只保留会被构建引用的测试脚手架**：凡被源码静态 import（如 e2e registry 被 registry-loaders 引用）的属于源码，随仓库走、不迁出；一旦该引用被移除，脚手架也应一并删掉，不要留下无人引用的死文件。

## 常见坑

- **跳过反向调研直接拆**：产出的任务卡里全是「在合适的模块中实现」，接手的人还得重新调研一遍，等于没拆。
- **只拆功能不拆脏活**：漏掉数据迁移、错误处理、埋点、兼容，会让实际工时翻倍。第 4 步的六个视角要逐条过。
- **任务卡写成 PRD 的复述**：任务卡要回答「代码怎么改」，不是「用户要什么」——后者是 PRD 的职责。
- **颗粒度太粗**：一张卡写了三天还没拆开，说明它其实是 Feature 不是 Task。
- **颗粒度太细**：把「加一个字段」这种十分钟的活单独成卡，会让任务表淹没在噪音里，应合并到相关任务。
- **一次抛出 20 个问题**：用户会失去耐心或草率回答。分批问（每次不超过 4 题），先问会改变拆解结构的——但每一条都要问到，不许因为「有推荐方案」就跳过。
- **把「带推荐方案」当成「不用问」**：推荐方案的价值是让用户确认/纠正只需一句话，不是省掉提问的借口。有疑问不问就拆，用户回一句「为什么不问」等于返工重来。
- **给出虚假精确的工时**：`3.5 天` 比 `S/M/L` 更容易被误当真。分级 + 说明理由更诚实。
- **假设项目里没有的东西**：所有「复用」判断都要有文件路径依据，不能凭印象。
- **凭 PRD 场景推导「新增」**：PRD 说筛选结构大改就判成新写组件，实际仓库里组件已存在、只是改造——回归面被低估，工作量估算失真。改动方式以路径存在性为准，不以 PRD 叙述为准。
- **只写「复用某组件」就交差**：任务卡没有设计稿区块对应关系时，执行方唯一的视觉依据就是组件默认样式，只能自由发挥——自造按钮尺寸、自创多列网格都是这么产生的。复用判断必须配设计锚点，视觉细节留给 ui-restore。
- **埋点不分类型、不写位置**：「加个埋点」这种任务卡没法验收——曝光埋点（进可视区域触发，用 `TrackBeseen`）误用成 `sendTrack`、或点击埋点误用 `TrackBeseen`，数据口径直接作废；点位没写到组件层级，实现时容易挂错位置（挂在列表容器而不是每个 item、挂在点击而不是确认通过后）。
- **把业务规则当"前端体验优化"拆给前端**：最典型的是「按钮置灰就不让点了」「前端校验一下就行」。前端置灰和校验只解决体验，接口照样能被直接调用——权限和业务规则的判定必须在后端，前端做的是把后端返回的 `canCancel`/`canEdit` 渲染成禁用态。
- **两端各做一遍**：同一个校验规则前后端各写一套、且两边各写各的，改一处忘一处就会出现线上不一致。规则由后端定、前端只做呈现时，要让前端从接口/枚举取规则，而不是重新抄一份。
- **只分端不分任务**：判定完归属就完事，没落成任务卡，结果还是没人知道具体要改哪个文件。
- **不问范围就默认全栈**：用户只要前端拆解，却产出了一堆后端任务卡——既浪费时间，也容易让用户误以为后端进度已有人跟进。
- **只拆一端就把另一端写没了**：只拆前端、不列接口依赖清单，任务卡里出现「等后端提供接口」却没人知道要提供什么。范围决定展开到多细，不决定另一端消失。
- **中途改范围只在原文上追加**：会导致两端任务口径不一致，应回到第 3 步重做切分表再补齐。

## 与后续流程的衔接

拆解完成后，用户说「开始做 T003」时交给 **task-runner** 执行。此时：

- 库里的实现要点是**输入**，不是最终答案——开工前仍要重新确认目标文件当前状态（`ptb task show` + 读真实代码）
- 执行中发现技术方案不成立，**回写任务记录**（`task text` / `task set`），而不是就地偏离后不记录
- 状态由 task-runner 通过 `ptb complete` 回写；本技能不维护进度，也不生成进度文件

### 与 contract-align 的交接

后端技术文档到位、用户说「对齐字段」时进入 contract-align 流程。拆解产物要为它备好三样东西：

1. **期望契约清单**（`contracts` / `contract_fields`）——对齐的「前端要什么」来源，用 `python3 "$PTB" contract list --jira <J>` 读取；
2. **`--kind contract` 标注的验收项**（`acceptance`）——contract-align 的回扫点：契约结论落地时这些验收项必须复核修剪；
3. **基线约束**（`jiras.baseline`）——contract-align 开工会逐条重申是否仍适用。拆解时为估工作量而设的约束，到对齐阶段可能恰恰应该解除，不许让它静默流过去。

### 与 ui-restore 的交接

任何含 UI 改动的任务开工前，由 ui-restore 负责视觉判定与落地——**本技能不执行还原，但交接不能断**，否则执行方手上只有组件名，只能按组件默认样式自由发挥。

交接三样：

1. **设计稿路径 + 覆盖的任务清单**——`design_drafts.path` 与 `covers`；一份设计稿对应一轮 ui-restore（不是每张卡各跑一遍）。
2. **已知视觉裁决**——用户或本流程已经拍板的、与设计稿不一致的决定（例如「整体布局复用项目既有页面，设计稿只校对控件级样式」「断点以项目为准」）。这类裁决必须写进 `jiras.baseline` 和任务的 `design_ref`；不写下去，下一个会话很可能按设计稿推翻重做。
3. **需回扫的视觉验收项**——`acceptance` 里 `kind=visual` 的条目，统一 `via=ui-restore`，由双宽度截图比对闭环。

回写要求：

- ui-restore 是独立技能，**不读也不写本库**；它的组件映射由自己落盘（默认写到设计稿同目录的 `<设计稿名>.mapping.json`），任务库只保留 `design_ref` 和验收结论；
- 映射判定（复用 / 需改造 / 新建）与任务记录冲突时，**以实际读过设计稿的一方为准**，由 task-runner 把结论回写任务（`task text` / `file add` / `acc add`）；用户裁决覆盖设计稿的，记入 `jiras.baseline`；
- 任务记录因此变更的文件、验收项同步更新，不留两套口径。
