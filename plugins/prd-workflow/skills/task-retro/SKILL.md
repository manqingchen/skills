# task-retro：纠正记录与技能升级

两个模式：**捕获**（每次验收后记一条）、**升级**（积累一段时间后把纠正变成规则）。

```bash
SKILL_DIR="$(cd "$(dirname "<本技能目录>/SKILL.md")" && pwd -P)"
PLUGIN_ROOT="$(cd "$SKILL_DIR/../.." && pwd -P)"
PTB="$PLUGIN_ROOT/scripts/ptb.py"
```

本技能只记录与升级，**不修代码**（那是 task-runner 或用户的事），**不改产品决策**。

---

## 模式一：捕获

### 触发

用户看完任务产出后说「这里和设计稿/需求不一致」「按钮要按稿子做成 X」「刚才改的那部分记一下」，或直接调用本技能。

### 步骤

1. **定位**：确认 `JIRA + 任务ID`。用户没说是哪条时，从上下文推断后复述确认；推断不出就问。
2. **取证据**：读任务记录与相关锚点，确保记的是事实不是印象：

```bash
python3 "$PTB" task show <TASK> --jira <JIRA> --json
python3 "$PTB" jira show --jira <JIRA> --md          # baseline、设计稿
```

3. **澄清三件事**（用户已说清就不问，最多一次问完 ≤4 项）：期望是什么、实际是什么、最终怎么改的。
   **不要自己补全**：用户的原始诉求是后续升级最重要的证据，宁可标「未说明」。
4. **归因**（每条必须给出，拿不准标 `unclear` 并给两个候选）：

| 归因 | 判断准则 |
|---|---|
| `prd-to-breakdown` | 拆解时信息没给到：缺设计锚点、缺契约字段、职责切分错、验收写空 |
| `task-runner` | 信息有但执行没遵守：没跑 Gate、没调 ui-restore、验收没真跑、没回写 |
| `ui-restore` | 还原过程取值错误：尺寸/颜色抄错、断点用错、复用判定错 |
| `unclear` | 证据不足以定位，或跨两层 |

`dimension` 取 `visual` / `requirement` / `contract` / `scope` / `docs`；`rule_gap` 写一句可执行的规则缺口（如「UI 任务必须有设计区块映射」），不要写「加强把控」这类空话。

5. **写入**：

```bash
python3 "$PTB" correction add --jira <JIRA> --task <TASK> --dimension visual --blame prd-to-breakdown \
  --instruction "卡片 WhatsApp 按钮按设计稿做成绿描边带文字" \
  --expected "设计稿 .car-whatsapp outline 变体" --actual "自造 20/28px 纯图标按钮" \
  --change "改为 .shopWhatsapp，PC 38px/13px，移动 34px/12px" \
  --root-cause "任务记录只有组件名，没有设计区块映射" \
  --rule-gap "UI 任务必须登记 design_ref 区块映射"
```

长文本用 `--xxx-file /tmp/xxx.md`。

6. **确保任务记录已同步**（如果本次修改还没有回写）：
   - 改了实现 → `task text --field implementation` 或 `notes`
   - 补了文件 → `file add`
   - 补了验收 → `acc add`
   - 用户裁决覆盖设计稿 → `jira set --baseline "..."`
7. 向用户回一条：纠正 ID + 归因 + 一句话规则缺口。**不要顺手改技能文件。**

### 捕获红线

- 不猜用户意图。原始诉求不清楚就标「未说明」，不要用你的推断填空；
- 不把一次纠正说成系统性问题。复发与否由升级阶段用数据判断；
- 不在捕获时改技能——捕获和升级必须分开，否则「一次事故写进永久规则」的过拟合就发生在你手里。

## 模式二：升级

### 触发

用户说「复盘一下」「升级技能」「最近老出什么问题」，或一段时间后主动建议（例如连续积累 5 条以上 open 纠正）。

### 步骤

1. **聚合**：

```bash
python3 "$PTB" correction cluster --since <YYYY-MM-DD>
python3 "$PTB" correction list --status open
```

2. **筛选**：只纳入**复发 ≥2 次**或**用户点名**的类别。单次偶发默认不升级，在汇报里列为「观察中」。判断「复发」看 `rule_gap` 语义是否同一类，不要只看字符串完全相同。

3. **提案**：每个候选给出具体改法，必须落到「文件 + 章节 + 怎么改」：

   > 目标：`prd-to-breakdown/SKILL.md` 第 5 步「设计锚点」
   > 改法：追加「任务含 UI 改动但未登记 design_ref 时，`validate` 直接报错，不得产出」
   > 覆盖纠正：`F-20261023-01`、`F-20261027-03`
   > 操作类型：新增 / 替换 / 合并（必须选一个）

   操作类型选「新增」时，说明为什么不能替换或合并现有规则。

4. **冲突检查**：新规则与现有硬规则逐条对撞。发现矛盾（例如与「复用优先」冲突）必须先解决，不能两条并存——否则执行时随机命中哪条，问题只会更隐蔽。

5. **等用户确认**。不确认不落地。用户否掉的提案：`python3 "$PTB" correction set --id <F> --status rejected`，并在汇报里记下否掉的原因（下次不要再提）。

6. **落地**（用户确认后）：
   - 编辑目标 SKILL.md（`prd-to-breakdown` / `task-runner`，视觉类才考虑 `ui-restore`）；
   - 结构性自查：章节完整、交叉引用可达、命令与 CLI 实际参数一致（跑一次 `--help` 对照）；
   - 用 **smart-commit** 提交，一条升级一个提交；
   - 记录升级，并把相关纠正置为 adopted：

```bash
python3 "$PTB" upgrade add --summary "任务产出增加 design_ref 必填校验" \
  --targets "prd-to-breakdown" --commit <哈希> \
  --corrections "F-20261023-01,F-20261027-03"
```

7. **效果回检**：升级后再观察同一 `dimension`/`rule_gap` 是否复发。复发说明改错了层（例如信息缺失却去加执行约束），下一轮升级要改层而不是加码。

### 防退化规则（升级时逐条遵守）

- **禁止单调膨胀**：每次只允许新增 / 替换 / 合并；SKILL.md 超过约 400 行先触发合并整理；
- **禁止把单次事故写成永久规则**：除非用户明确点名这是硬红线；
- **禁止把具体事实写成规则**：某个按钮 38px 属于设计稿事实，不该进技能；
- **保留拒绝记录**：`rejected` 的提案不再原样重提；
- **一次升级只动一个技能**（跨技能改动拆成多次），否则效果无法归因。

## 与其他技能的接口

| 技能 | 关系 |
|---|---|
| prd-to-breakdown | 读它的任务与决策记录；升级时可能是修改对象 |
| task-runner | 读它回写的完成记录与验收结果；升级时可能是修改对象 |
| ui-restore | 视觉纠正的归因对象之一；只在视觉类复发时考虑升级，且需用户单独确认 |
| smart-commit | 升级落地后的提交执行者 |

## 常见错误

- 捕获时替用户补全意图：证据失真，后续升级基于错误前提；
- 归因一律写 `task-runner`：信息缺失和执行违规的修法完全不同，归错层等于白改；
- 每条纠正都立刻改技能：规则膨胀、过拟合，且无法判断哪条改动有效；
- 只改技能不记录 `upgrade`：下次复盘不知道改过什么，重复提案；
- 升级后不看复发：改完就认为解决了，问题会以同样形态再来一次。
