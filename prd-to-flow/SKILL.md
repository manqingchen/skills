# PRD → Flow：需求拆解为可执行任务流

把一份 PRD 变成「每个任务都能被一个人、独立、在一天内做完并验证」的任务流。

**核心原则：拆解的质量取决于对现有代码的理解，而不是对 PRD 的复述。** PRD 只告诉你「要什么」，代码库才告诉你「从哪儿改、改多少、会和谁冲突」。所以本流程的第二步（反向调研）通常比第一步更花时间，不要跳过。

---

## 流程总览

```
0. 读取 PRD          → 拿到原始需求，确认范围边界
0.5 确认拆解范围      → 问清这次拆「前端 / 后端 / 前后端」，之后所有步骤按此聚焦
1. 反向调研当前项目   → 摸清技术栈 / 模块结构 / 既有约定 / 可复用实现
2. 差异与缺口检查     → PRD × 现状 对不上或说不清的地方，列出来问用户
3. 职责归属切分       → 逐条需求判定：前端做 / 后端做 / 前后端都做（各做什么）
4. 需求拆分          → Epic → Feature → 任务卡（颗粒度：可独立开发+可验证）
5. 技术落点          → 每条任务写清涉及文件、改动方式、接口/数据结构变化
6. 依赖与排期        → 依赖图、可并行分组、里程碑切分
7. 产出文档          → 拆解文档 + 技术方案 + 任务卡
8. 自检             → 逐条对照检查清单
```

各步骤之间**不要跳步**。第 2 步发现的每一个需要拍板的问题都必须真的问出去、等到用户回答之后才能继续拆——带推荐方案也不例外（推荐是为了让用户确认/纠正只需一句话，不是跳过提问的理由）。问题多时分批问（每次不超过 4 题），但必须批完所有问题，不允许「问几条、其余写进文档」；用户拒绝回答某一批时，把问题用文字列出来请其在对话里回复，回复前对应条目不得当作已确认。只有用户明确说「别问了直接拆 / 按推荐执行」，才允许把问题降级为文档里的「待确认」标注继续。**第 0.5 步的范围确认同样必须真的问**——不要默认拆全栈。

---

## 0. 读取 PRD

从以下来源之一拿到需求：

- 用户消息里直接粘贴的需求文本
- 用户给出的文件路径（`.md` / `.docx` / `.pdf` / `.txt` / 网页链接），用 Read / WebFetch 读取
- 项目里的 PRD 目录（常见位置：`docs/`、`doc/`、`prd/`、`需求/`、`requirements/`、`*.prd.md`）
- 飞书/语雀/Confluence 等链接——如果无法直接访问，明确告诉用户读取失败，请他们粘贴内容

拿到后先做三件事，都要在回复里简短说明：

1. **需求清单化**：把 PRD 里所有「要做什么」编号列出（R1、R2……）。这一步是为了后面能逐条对齐，避免拆着拆着漏了。
2. **范围边界**：明确写出**不做什么**（PRD 里说"暂不支持/后续迭代"的，以及明显属于其他需求的）。边界不清的需求是范围蔓延的源头。
3. **识别缺失的验收标准**：PRD 常常只写功能不写验收。哪条需求你无法判断「做完没有」，记下来，进入第 2 步提问。

> 如果输入根本不是需求文档（例如是一份 bug 列表、一份代码 review 意见），先跟用户确认这是不是要拆的对象，不要硬套本流程。

---

## 0.5 确认拆解范围（前端 / 后端）

**读完 PRD、动任何调研之前，先问这一句。** 范围决定后面所有步骤的聚焦面：反向调研扫哪些目录、职责切分表填几列、任务卡产出哪一端、排期按哪一端的工时算。

### 引导提示（照这个问）

读完 PRD 后，先给出一句话的需求概括，再问：

> **这次要拆的是哪一端？**
> - **A. 只拆前端**——我按前端视角拆，后端只作为依赖列出（需要哪些接口、要什么字段）
> - **B. 只拆后端**——我按后端视角拆，前端不展开，但要给出接口契约供前端对接
> - **C. 前后端都拆**（默认）——完整职责切分 + 两端任务卡，并标出哪些能并行

如果 PRD 里已经明确限定（例如通篇只讲页面改版、或明确是接口/数据层需求），不要机械发问——直接说出你的判断和依据，让用户确认或反驳：

> 「这份 PRD 通篇是页面交互和样式调整，没有接口和数据变更，我按**只拆前端**来做。如果后端也有改动，告诉我一声。」

### 三种范围下的产出差异

| 范围 | 反向调研 | 职责切分表 | 任务卡 | 技术方案 |
|---|---|---|---|---|
| **A 只前端** | 只扫前端目录、组件库、请求封装、状态管理 | 仍要填全，重点在「前端不处理」列——明确列出哪些逻辑**等着后端给** | 只出前端卡 | 前端改动细节 + **接口依赖清单**（要调什么、要什么字段、谁提供、是否已存在） |
| **B 只后端** | 只扫服务端目录、数据层、路由与中间件 | 仍要填全，重点在后端职责 | 只出后端卡 | 数据模型 + **接口契约**（前端拿这份就能开发）+ 迁移与回滚 |
| **C 都拆** | 两端都扫 | 完整 | 两端卡分列 | 完整 |

### 关键：只拆一端 ≠ 另一端可以不知道

即使只拆一端，也要产出「另一端依赖清单」，否则接不上：

- **只拆前端时**，必须列出：需要调哪些接口、每个接口要什么字段、接口是否已存在（存在则写路径，不存在则标「待后端提供」并写出期望契约）。这些是前端能不能开工的前提，缺了这份清单，前端任务卡里就会出现「等后端」的阻塞项而没人知道卡在哪里。
- **只拆后端时**，必须给出接口契约的完整定义（字段、枚举、错误码、分页），这是交给前端的交付物。没有它前端无法并行开工。

> **范围只影响「展开到多细」，不影响「另一端完全消失」。** 另一端永远以「依赖 / 契约」的形式在文档里出现。

### 记录范围

确认后，把结论写进拆解文档的头部信息表和 `README.md`，并在后续对话中始终按此范围产出。用户中途改范围（例如「后端也一起拆了吧」）时，回到第 3 步重做职责切分表，再补出另一端的任务卡——不要只在原文档上追加，那会导致两端口径不一致。

## 1. 反向调研当前项目

**按第 0.5 步确认的范围聚焦调研面**：只拆前端就只扫前端目录，不必花时间读服务端代码；只拆后端同理。唯一例外是查明「另一端是否已有可复用的实现」——这仍然值得扫一眼，能避免把已有的接口又拆一遍。

**目的：让每条任务卡里写的是真实的文件名和真实的函数名，而不是「在相关模块中添加逻辑」。**

### 调研方式

先判断项目规模：

- **小项目（< 约 50 个源文件）**：直接自己用 Glob / Grep / Read 扫。
- **中大型项目**：用 Agent 工具并行派发调研子任务（各 agent 一个主题，互不重叠），再汇总。典型分工：
  - agent A：整体架构——技术栈、目录结构、构建/启动方式、依赖清单
  - agent B：与本需求相关的业务模块——现有哪些类似功能、代码在哪儿
  - agent C：数据层——数据模型、表结构、迁移方式、ORM 约定
  - agent D：接口层——路由组织方式、鉴权方式、请求/响应约定、错误码规范

派发时要求 agent **只回结论 + 文件路径 + 关键代码位置**，不要回大段代码原文。

### 必须搞清楚的六件事

| # | 要搞清的问题 | 为什么重要 |
|---|---|---|
| 1 | 技术栈与版本、构建与启动命令、测试命令 | 任务卡里的验收步骤要能真跑起来 |
| 2 | 模块划分与目录约定 | 决定新代码该放哪儿 |
| 3 | 数据模型与持久化方式（表、迁移、ORM） | 需求改动常从数据开始 |
| 4 | 接口/组件约定（路由、鉴权、错误处理、状态管理、样式方案） | 新代码必须和既有写法一致 |
| 5 | **是否已有相似实现可复用或需改造** | 这是拆解时最大的信息量来源 |
| 6 | 约束与坑（遗留代码、正在进行的重构、已知技术债、必须兼容的旧版本） | 决定哪些任务风险高、要单独拆 |

### 输出：项目现状摘要（Project Brief）

在正式拆解前，用一段简短的话说明：

- 技术栈一句话（语言/框架/数据库/关键库）
- 与本需求相关的模块地图（3~7 个模块，各自职责 + 关键文件路径）
- 现有相似实现（如果有，指出路径，并判断「复用 / 改造 / 新写」）
- 约定清单（命名、目录、接口风格、测试方式）
- 风险与约束

这份摘要要放进最终文档，它是后面所有任务卡能落到具体文件的依据。

## 2. 差异与缺口检查

把 PRD 和项目现状放在一起对，找出需要用户拍板的问题。**分类找，别泛泛地问「还有补充吗」。**

### 四类缺口

1. **PRD 内部矛盾或遗漏**
   - 同一条需求前后描述不一致
   - 只写了正常流程，没写异常流程（失败、超时、空数据、越权、并发）
   - 只写了功能，没写边界（数量上限、字段长度、超大文件、重复提交）
   - 没有验收标准，无法判断做完没有

2. **PRD 与现状冲突**
   - PRD 描述的行为和现有代码逻辑不一致（要改旧行为？还是新增分支？）
   - 依赖的能力当前项目没有（需要引入新库/新服务/新权限）
   - 数据模型对不上（PRD 里要的字段现有表里没有，且涉及历史数据迁移）

3. **范围与优先级不明**
   - 多条需求里哪条是必须的、哪条可以延后
   - 是否需要数据埋点、灰度开关、兼容旧版本
   - 多端（Web / iOS / Android / 小程序 / 服务端）分别要做什么

4. **交付约束不明**
   - 截止时间、可投入人力、是否需要拆分给多人并行
   - 是否要求不破坏线上数据、是否需要回滚方案

### 提问格式

**先调研、带方案地提问**，不要空手问。对每个问题给出你基于代码调研得出的**推荐答案**，用户只需要确认或纠正——这比开放式提问快得多：

```markdown
### 待确认问题

**Q1. 旧数据的 `status` 字段如何迁移？**
- 现状：`orders` 表已有 `status`（0/1/2），本次 PRD 要求改为 5 个状态
- 推荐：新增 `status_v2` 字段 + 双写 + 后台任务回填，旧字段保留一个版本周期
- 备选：直接改枚举值并一次性刷数据（有回滚风险）
→ 需要你确认走哪种
```

**问题多时分批问完，不许降级**：数量多不要一次全抛。先问会**改变拆解结构**的（范围、数据模型、是否改造旧逻辑），再问产品口径类的（字段命名、埋点口径、交互取舍、频控归属、异常处理策略），分批把**所有**问题问完。判断「要不要问」的标准是**这条是否需要人拍板**，而不是「是否改变拆解结构」——凡涉及用户可感知行为、数据口径、跨端职责的问题都必须问，即使你已有明确的推荐答案。唯一例外：用户明确说「别问了，按推荐直接拆」。

## 3. 职责归属切分（前端 / 后端）

**这一步必须在拆分之前做。** 归属没定清楚就拆任务，会出现三种典型事故：前后端各做一遍同一件事；都以为对方会做，最后线上没人做；把后端该管的业务判断塞给前端，导致多端（Web/iOS/Android/小程序）逻辑不一致且能被绕过。

**判断准则只有一条：这段逻辑放在前端，会不会导致「换个客户端就能绕过它」或「需要在多个端重复实现」？会——就是后端的。**

### 三层归属模型

| 层 | 归属 | 内容 |
|---|---|---|
| **展示与交互层** | 前端 | 渲染、样式、布局、动画、交互反馈、loading/空态/错误态、输入框即时校验与错误提示位置、表单收集 |
| **业务逻辑层** | **后端** | 业务规则、状态流转、金额与库存计算、发号、去重、幂等、权限判定、数据范围过滤（数据权限）、审批流 |
| **校验层** | **前后端各做一次，职责不同** | 前端：为了即时反馈、提升体验，不做安全保证<br>后端：**唯一的强制校验**，任何请求都当作不可信 |
| **契约与枚举层** | **后端维护，前端消费** | 状态枚举、错误码、字典表、展示格式化规则（金额精度、时间格式、脱敏规则）、分页结构 |

### 速查：这些逻辑不让前端处理

- 权限与角色判断——前端只控制"按钮显不显示"，后端必须独立校验；前端隐藏了按钮不等于接口安全
- 业务规则与状态机——"这个状态能不能取消""满足什么条件才能提交"由后端裁决，前端只按后端返回的可操作标记来渲染
- 金额、库存、价格、优惠、积分的计算——前端不做，浮点误差和并发超卖都会出事
- 数据过滤与范围——"只看自己部门的""只看自己创建的"由后端在查询层保证
- 幂等与去重——重复提交由后端用幂等键/唯一约束兜底，前端禁用按钮只是体验优化
- 枚举含义、错误码、字典映射——后端维护，前端不硬编码业务含义
- 跨端共用的业务逻辑——只要有两个以上客户端，逻辑就必须在后端
- 数据一致性相关的串联操作（下单扣库存、退款改状态）——后端事务

### 速查：这些不该让后端处理

- 展示格式化中纯本地的部分（如宽度自适应、本地化排布）
- 纯 UI 状态（展开/收起、当前 tab、hover）——不必往返服务端
- 输入框的即时格式提示（手机号规则、必填标记）——但后端仍要独立校验一次

### 输出：职责切分表

对**每一条需求**（R1、R2……）填一行，不允许留空：

| 需求 | 前端职责 | 后端职责 | 前端不处理（明确排除） | 归属结论 |
|---|---|---|---|---|
| R1 订单取消 | 取消按钮、二次确认弹窗、结果 toast、列表状态刷新 | 状态机校验、权限校验、库存回补、写操作日志 | 不做"能否取消"的判断，只消费接口返回的 `canCancel` | 后端主导 / 前端对接 |
| R2 状态时间线 | 时间线组件、空态展示 | 提供历史接口、排序、老数据兼容 | 不前端拼接时间文案，展示格式由后端给定 | 后端提供数据，前端纯展示 |

**「前端不处理」这一列是必须的**，它才是这一步真正的价值——明确排除项能防止开发者出于"顺手"把业务逻辑写进组件里，那正是后面多端不一致的源头。

### 特殊情况

- **纯前端需求**（样式调整、无接口改动）：后端职责写「无」，并注明"不涉及接口变更"
- **纯后端需求**（定时任务、数据修复）：前端写「无」，并注明"对前端不可见"
- **一个需求内混合**：切成两条任务卡（前端卡 + 后端卡），中间以接口契约连接，接口契约作为独立的先行任务
- **归属有争议时**：列入第 2 步的待确认问题，带推荐方案问用户——这属于会改变拆解结构的决策，值得问

详细判断规则与反模式见 `references/frontend-backend-split.md`，拆解前读一遍。

## 4. 需求拆分

### 层次结构

```
Epic（本次需求的几个大块，通常 2~5 个）
  └── Feature（用户可感知的功能单元，每个 Epic 下 2~6 个）
        └── Task（任务卡：可独立开发、可独立验证）
```

### 任务卡的颗粒度标准

一条任务卡**必须**同时满足：

- **一个人**能做（不需要多人同步协调）
- **一次会话 / 一天内**能做完（超过就继续拆）
- **有明确的完成信号**（能跑一个命令、点一个页面、过一条断言来验证）
- **不依赖未完成的其他任务**——或者依赖关系在卡里写明了

拆得不够：`「实现订单模块」`、`「优化性能」`、`「对接第三方」`
拆得合适：`「新增 GET /api/orders/{id}/timeline 接口，返回状态变更历史」`、`「订单列表页接入分页，默认每页 20 条」`

**如果一条任务卡里出现了"并且"、"同时"、多个动词——继续拆。**

### 拆分视角（按顺序都过一遍，避免漏任务）

1. **数据层**：表/字段/索引变更、数据迁移、数据回填脚本
2. **服务端**：接口、业务逻辑、校验、权限、定时任务、第三方对接
3. **前端/客户端**：页面、组件、状态管理、路由、请求封装、交互细节（loading / 空态 / 错误态）
4. **联调与配置**：接口联调、开关配置、环境变量、CI 变更
5. **测试**：单元测试、集成测试、手工验证用例
6. **交付配套**：埋点、监控告警、灰度、文档、回滚方案

> **不要漏掉"看不见的活"**：数据迁移、错误处理、权限校验、埋点、兼容旧数据、日志监控。这些往往占实际工作量的一半，漏掉它们会让排期失真。

---

## 5. 技术落点

每条任务卡里写清楚「改哪儿、怎么改」，这样接手的开发者（或另一个 agent）不用重新调研。

对每条任务写明：

- **端归属**：前端 / 后端 / 联调。来自第 3 步的职责切分表，不要在这里临时改判
- **涉及文件/模块**：具体路径，能到文件级别就到文件级别（`src/api/order.ts`、`internal/handler/order.go`）
- **改动方式**：新增文件 / 修改现有函数 / 删除 / 重构
- **接口契约**：新增或变更的 API——方法、路径、请求体、响应体、错误码
- **数据结构**：新增或变更的表字段、类型定义、状态枚举
- **复用点**：可以复用的现有函数、组件、工具类（写路径）
- **风险点**：兼容性、并发、性能、数据一致性上的注意项

**接口契约是前后端任务的连接点，必须单独成卡或单独成节。** 前端任务卡只引用契约，不重新定义字段名；后端任务卡是实现契约的一方。契约先行，前后端才能并行开发——否则前端只能等后端写完。

**不要写实现代码**。技术方案止于「契约与落点」，写代码是执行阶段的事。

---

## 6. 依赖与排期

- **依赖图**：明确标出 A 必须先于 B（`T3 依赖 T1、T2`）。跨模块的接口契约类任务应当排在依赖它的开发任务之前——先定契约，再并行开发。
- **可并行分组**：把无依赖关系的任务分组，标注「可并行」和「建议并行开发人数」。
- **里程碑**：按"能跑通/能演示"的节点切分。例如 M1 数据层就绪、M2 后端接口可用、M3 前端联调完成、M4 测试与灰度。每个里程碑写清**可验证的产出**，而不是「大致完成」。
- **关键路径**：指出哪条链路决定整体工期，这是排期风险点。
- **工作量估计**：用 S（半天内）/ M（1~2 天）/ L（3~5 天）分级，并说明理由。不要给没有依据的精确小时数。

## 7. 产出文档

### 输出位置

**所有产出统一写到 `~/.claude/prd-flow/workspace/<JIRA号>/`，不写进业务仓库。** 需求文档是个人工作产物，不进 git、不占仓库状态。

```
~/.claude/prd-flow/
├── README.md                       ← 入口：所有需求的总索引
└── workspace/
    ├── PROJ-123/                   ← 一个 Jira 号一个目录
    │   ├── README.md               需求索引：一句话概括、状态、文件导航
    │   ├── 01-breakdown.md         需求拆解文档（项目现状摘要、需求清单、职责切分表、缺口问答）
    │   ├── 02-tech-design.md       技术方案（整体设计 + 接口契约 + 每条任务的落点）
    │   ├── i18n.md                 多语言映射（有则产出）
    │   └── tasks/
    │       ├── README.md           任务总览表（ID / 标题 / 端 / 依赖 / 估计 / 状态 / 负责人）
    │       ├── T001-xxx.md         单条任务卡
    │       └── ...
    └── PROJ-456/
        └── ...
```

**目录名取 Jira 号**（如 `PROJ-123`）。Jira 号一般在 PRD 的「Jira」字段里，格式形如 `[PROJ-123](...)`。若 PRD 里没有 Jira 号，用需求的 kebab-case 短名代替，并在 `~/.claude/prd-flow/README.md` 里标注「无 Jira 号」。

> ⚠️ **不要用当前工作目录名当目录名。** 业务仓库常以 git worktree 工作，worktree 目录名虽也是 Jira 号，但 worktree 会随任务创建/清理，路径不稳定。始终以 PRD 里写的 Jira 号为准。

**目录已存在时**（同一 Jira 号重复拆解，例如中途改了范围）：直接覆盖对应文件，不要新建 `PROJ-123-2`。若本次拆解产出了上次没有的文件（如新增 `i18n.md`），一并补齐。

### 每完成一次拆解，都要更新总索引

`~/.claude/prd-flow/README.md` 是入口，每次产出后必须追加/更新一行：

```markdown
| Jira | 需求 | 状态 | 范围 | 产出日期 | 路径 |
| --- | --- | --- | --- | --- | --- |
| [PROJ-1234](https://jira.example.com/browse/PROJ-1234) | 商品搜索优化（AB实验） | 已拆解 | 仅前端 | 2026-09-18 | [workspace/PROJ-1234/](./workspace/PROJ-1234/) |
```

状态取值：`已拆解` / `开发中` / `已完成` / `已废弃`。重复拆解同一需求时更新该行，不要重复追加。

目录首次创建时，同时初始化 `~/.claude/prd-flow/README.md`（含标题、用途说明、索引表格表头）。

### 自检时额外确认

- [ ] 产出落在 `~/.claude/prd-flow/workspace/<Jira号>/`，**没有**写进业务仓库
- [ ] 目录名取自 PRD 里的 Jira 号，不是 `pwd` 的目录名
- [ ] `~/.claude/prd-flow/README.md` 的索引行已更新（新增或覆盖）

### 输出语言

跟随 PRD 的语言。若 PRD 是中文，文档用中文写，但文件名、代码标识符、接口路径、技术术语保留英文原样。若用户指定了语言，以用户为准。

### 文档模板

模板见：
- `references/breakdown-template.md` —— 拆解文档 + 技术方案结构
- `references/task-card-template.md` —— 任务卡结构 + 前后端任务卡正反例
- `references/frontend-backend-split.md` —— 前后端职责切分规则（第 3 步执行前读）

**每次产出都读一遍模板**，不要凭记忆写，避免结构漂移。

### 文档排版要求

- 任务清单用 Markdown 表格，带可勾选的 `- [ ]` 状态列
- 任务 ID 稳定（`T001`），后续对话里只用 ID 指代任务
- 每条任务卡里都要有「验收标准」，且必须是**可观测**的（能跑命令 / 能点页面 / 能看日志），不能是「功能正常」这种空话
- 需求清单（R1、R2……）和任务卡要做**双向映射**：每条需求能查到它对应哪些任务，每条任务能查到它在满足哪条需求
- 每条需求都要有明确的端归属，且在拆解文档和任务卡里**保持一致**
- 接口契约在文档里只定义一次（在 `02-tech-design.md`），任务卡引用而不复制，避免前后端两份字段名对不上

## 常见坑

- **跳过反向调研直接拆**：产出的任务卡里全是「在合适的模块中实现」，接手的人还得重新调研一遍，等于没拆。
- **只拆功能不拆脏活**：漏掉数据迁移、错误处理、埋点、兼容，会让实际工时翻倍。第 4 步的六个视角要逐条过。
- **任务卡写成 PRD 的复述**：任务卡要回答「代码怎么改」，不是「用户要什么」——后者是 PRD 的职责。
- **颗粒度太粗**：一张卡写了三天还没拆开，说明它其实是 Feature 不是 Task。
- **颗粒度太细**：把「加一个字段」这种十分钟的活单独成卡，会让任务表淹没在噪音里，应合并到相关任务。
- **一次抛出 20 个问题**：用户会失去耐心或草率回答。分批问（每次不超过 4 题），先问会改变拆解结构的——但每一条都要问到，不许因为「有推荐方案」就跳过。
- **把「带推荐方案」当成「不用问」**：推荐方案的价值是让用户确认/纠正只需一句话，不是省掉提问的借口。有疑问不问就拆，用户回一句「为什么不问」等于返工重来。
- **给出虚假精确的工时**：`3.5 天` 比 `S/M/L` 更容易被误当真。分级 + 说明理由更诚实。
- **假设项目里没有的东西**：所有「复用」判断都要有文件路径依据，不能凭印象。
- **把业务规则当"前端体验优化"拆给前端**：最典型的是「按钮置灰就不让点了」「前端校验一下就行」。前端置灰和校验只解决体验，接口照样能被直接调用——权限和业务规则的判定必须在后端，前端做的是把后端返回的 `canCancel`/`canEdit` 渲染成禁用态。
- **两端各做一遍**：同一个校验规则前后端各写一套、且两边各写各的，改一处忘一处就会出现线上不一致。规则由后端定、前端只做呈现时，要让前端从接口/枚举取规则，而不是重新抄一份。
- **只分端不分任务**：判定完归属就完事，没落成任务卡，结果还是没人知道具体要改哪个文件。
- **不问范围就默认全栈**：用户只要前端拆解，却产出了一堆后端任务卡——既浪费时间，也容易让用户误以为后端进度已有人跟进。
- **只拆一端就把另一端写没了**：只拆前端、不列接口依赖清单，任务卡里出现「等后端提供接口」却没人知道要提供什么。范围决定展开到多细，不决定另一端消失。
- **中途改范围只在原文上追加**：会导致两端任务口径不一致，应回到第 3 步重做切分表再补齐。

## 与后续流程的衔接

拆解完成后，用户通常会接着说「开始做 T003」之类。此时：

- 任务卡里的技术方案是**输入**，不是最终答案——真开始写代码时仍要重新确认目标文件当前的状态（文件可能已变动）
- 如果执行过程中发现任务卡的技术方案不成立，**回头更新任务卡**，而不是就地偏离——否则文档会迅速失效
- 完成一条就更新 `tasks/README.md` 里的状态，保持任务表是可信的进度来源
