# 任务卡模板

每条任务一个文件：`tasks/T001-<kebab-case-slug>.md`。

**填写原则**：任务卡回答的是「代码怎么改」，不是「用户要什么」——后者属于 PRD。每一栏都要写具体路径、具体函数、具体命令，不出现「相关模块」「适当处理」这类模糊表达。

## 示例：合格的任务卡

```markdown
# T003 新增订单状态时间线接口

| 项 | 内容 |
|---|---|
| 所属 Epic | E1 订单状态可视化 |
| 端 | 后端 |
| 类型 | 服务端 |
| 满足需求 | R2 |
| 依赖 | T001（需要 status_v2 字段就绪） |
| 估计 | M |
| 可并行 | 是 |
| 状态 | 待开始 |

## 目标

提供接口返回单个订单的状态变更历史及可操作性标记，供前端时间线组件消费。

## 本任务不负责

- 时间线的视觉呈现、空态文案 → 由 T006 [前端] 负责
- 「能否取消」的展示逻辑 → 本任务只返回 `canCancel` 标记，前端据此渲染

## 涉及文件

| 文件 | 改动方式 | 说明 |
|---|---|---|
| `internal/handler/order.go` | 修改 | 新增 GetOrderTimeline 处理函数 |
| `internal/service/order.go` | 修改 | 新增 ListStatusHistory 业务方法 |
| `internal/router/router.go` | 修改 | 注册路由，鉴权中间件参照同文件 order detail 路由 |

## 实现要点

1. 路由注册方式参照 `internal/router/router.go:42` 已有的 order detail 路由
2. 查询复用 `internal/repo/order_repo.go` 的 `FindByID`，不要新写 SQL 拼接
3. 时间线按 `created_at DESC` 排序，前端不再二次排序

## 接口 / 数据结构变更

契约以 `02-tech-design.md` 第三节为准。本任务是该契约的**提供方**。

`GET /api/orders/{id}/timeline`，响应：

```json
{ "code": 0, "data": { "items": [{ "status": 1, "canCancel": false }] } }
```

## 边界与异常

- 订单不存在 → 404，错误码复用 `ErrOrderNotFound`
- 无权限（非本人订单且非管理员）→ 403。**此校验在接口层强制执行，不依赖前端隐藏入口**
- 时间线为空（老数据无历史记录）→ 返回空数组，不返回 404
- 订单状态为终态时 → `canCancel: false`，并给出 `cancelDisabledReason`

## 验收标准

- [ ] `curl -H "Authorization: $TOKEN" localhost:8080/api/orders/123/timeline` 返回 `code:0` 且 items 按时间倒序
- [ ] 请求不存在的订单 ID 返回 404 且 body 含 `ErrOrderNotFound`
- [ ] 用他人订单 ID 直接调接口（绕过前端）返回 403
- [ ] 已发货订单返回 `canCancel: false` 且带 `cancelDisabledReason`

## 备注

老数据（T001 之前创建的订单）无历史记录，前端需处理空数组，见 T006。
```

## 示例二：前端任务卡（与上一条配套）

```markdown
# T006 订单状态时间线组件

| 项 | 内容 |
|---|---|
| 所属 Epic | E1 订单状态可视化 |
| 端 | 前端 |
| 类型 | 前端 |
| 满足需求 | R2 |
| 依赖 | T003（接口契约就绪即可开工，不必等 T002 写完） |
| 估计 | M |
| 可并行 | 是 |
| 状态 | 待开始 |

## 目标

在订单详情页展示状态变更时间线，并对不可取消的订单正确渲染禁用态。

## 本任务不负责

- 不判断订单能否取消 → 消费接口返回的 `canCancel` / `cancelDisabledReason`
- 不拼接状态文案与顺序 → 使用接口返回的顺序与文本，前端不重排、不映射业务含义
- 不做时间线的数据聚合 → 后端已聚合

## 涉及文件

| 文件 | 改动方式 | 说明 |
|---|---|---|
| `src/views/OrderDetail/Timeline.vue` | 新增 | 时间线组件 |
| `src/api/order.ts` | 修改 | 新增 getTimeline 方法，参照同文件 getOrderDetail 写法 |
| `src/api/types.ts` | 修改 | 新增 TimelineItem 类型 |

## 实现要点

1. 请求封装参照 `src/api/order.ts:18` 的 getOrderDetail
2. 状态点颜色用现有的 `src/styles/theme.ts` 色板，不新增颜色常量
3. 三种状态都要实现：加载中（骨架屏）、空数据（"暂无记录"）、请求失败（重试按钮）

## 接口 / 数据结构变更

契约以 `02-tech-design.md` 第三节为准。本任务是该契约的**消费方**，字段名以契约为准，不自行命名。

## 边界与异常

- 空数组 → 展示"暂无记录"，不报错、不留白
- 请求失败 → 展示重试入口，不静默失败
- `canCancel: false` → 取消按钮禁用，hover 显示 `cancelDisabledReason`

## 验收标准

- [ ] 打开 `/order/123`，时间线按接口返回顺序渲染
- [ ] 接口返回空数组时展示"暂无记录"
- [ ] 后端返回 `canCancel: false` 时取消按钮为禁用态，且展示后端返回的禁用原因
- [ ] 断网后打开页面，展示重试按钮，点击可重新请求

## 备注

依赖契约冻结即可开发，可用 T003 提供的 mock 数据先行联调。
```

## 反例：不合格的任务卡

| 写法 | 问题 |
|---|---|
| `## 目标：实现订单模块` | 颗粒度太粗，是一周的活，应该继续拆 |
| `## 涉及文件：相关后端文件` | 没有具体路径，接手者还得重新调研 |
| `## 实现要点：按照项目规范实现` | 等于没写，必须指明参照哪个文件 |
| `## 验收标准：功能正常可用` | 不可观测，无法判断做完没有 |
| `## 边界与异常：（空）` | 异常流程不是可选项，空数据/越权/重复提交必须考虑 |
| `## 本任务不负责：（空）` | 前后端会重叠或互相推诿，边界必须显式声明 |
| 前后端合成一张卡 | 无法分配给两人并行，且第 3 步的归属判定白做了 |
| 前端卡里写「前端校验手机号格式，不合法则拦截提交」 | 校验可做，但不能是唯一防线；且应注明后端仍独立校验，规则单一来源 |
| 后端卡里写「入参由前端保证」 | 把安全责任推给了客户端，可以直接被绕过 |
| 前端卡里自己定义接口字段名 | 契约必须单一来源，否则前后端字段对不上 |
| `## 埋点：加个曝光/点击埋点` | 没写挂在哪个组件、什么时机触发，也没按类型选 API（曝光 → `TrackBeseen`，点击 → `sendTrack`），无法验收且口径易错 |
